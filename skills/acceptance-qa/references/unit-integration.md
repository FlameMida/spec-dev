# 单元 / 集成 / 接口验收（Tier D）

> 清单含相应检查时读取。TDD 负责开发与补测纪律，本页负责验收时核对测试证据和覆盖缺口。

## 取得真实执行入口

从目标项目的配置或已批准的计划取得实际命令、工作目录和测试范围。使用该项目的包管理器与 runner；monorepo 先定位实际的 package。不从通用的技术栈命令表猜入口，不安装额外工具，不在仓库根盲跑。

## 证据与执行范围

1. 先看已有结果：计划里的红转绿记录、对应提交和测试文件。它们仍适用于当前候选版本时直接引用。
2. 检查测试是否真的执行到目标断言。零测试、SKIP、环境错误都不代表业务通过。
3. 核对选中的 Scenario 是否有对应测试以及断言从何而来，不按文件存在或覆盖率数字推断行为已完成。
4. 重新运行测试套件属于回归，范围由用户在询问门或直接调用时决定；没有选中就不跑。
5. 既有 warning、范围外的失败和本次引入的回归分别记录，不把验收扩大成清理所有历史告警。

## 接口契约与副作用

按接口的实际契约验证状态、响应字段与类型、错误语义，以及应该发生或不应该发生的业务效果。只收到成功状态码不足以证明有副作用的操作已经完成；需要的持久化、权限或重复请求行为在公共边界上验证。

没有响应体的契约不强求 JSON 字段；错误路径只覆盖本接口实际存在且清单要求的状态与语义，不机械补齐 400、401、404、409。边界、权限、失败后的状态以及重试和幂等要求有契约时不能遗漏。

认证和测试数据使用已有配置及授权边界，凭据不写进源码或报告。替身结果只证明本地消费者；真实数据库、服务或组合行为需要相应的真实证据。

## 覆盖率与专项工具

覆盖率门槛只来自项目现有配置；没有门槛时数字仅供参考，不自行发明百分比，也不用高覆盖率替代行为断言。

变异、模糊或消费者契约测试只在目标风险、已有能力与用户授权都适合时使用。记录环境条件、成本和未覆盖的范围，不为验收默认引入一套新的测试平台。
