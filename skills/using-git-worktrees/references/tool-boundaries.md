# Worktree 内的工具与命令

> 阅读时机：建立或恢复隔离后、首次绑定/写入前，以及宿主报告工作区隔离拒绝时。主线程与 implementer 各自核对自己的工具上下文。

新建目录与工具选择统一消费 [using-git-worktrees Step 1](../SKILL.md#step-1创建隔离工作区)：项目根 `.worktrees` 约束先于原生工具偏好。本专题不取消自动降级到 Git 原生 worktree：宿主原生隔离工具不可用、不能确认使用目标路径或创建失败时，保留 `git worktree` 降级路径，并核对实际失败原因、目标目录和授权范围。下面关于保留现有工作区、禁止为命令拒绝重建现场的规则，只处理已经建立隔离后的执行与恢复。

## 执行能力与管理方式分别核验

这是一份通用执行约定，适用于主线程、并发实施、集成组、测试、审查和交付，不按某个项目、语言、formatter 或 CLI 子命令提供放行特例。

开始受保护写入或派发前，根据本次实际计划列出需要的能力：目标 cwd 能否传入并保持、文件工具是否在同一工作区、Git 命令与任务绑定能否运行、锁和进度是否有符合原子性要求的执行入口。证据使用宿主实际接口、官方行为说明和同版本的有效运行回执；未知就明确未知，不能用“工具存在”“路径可读”“inspect 成功”替代写入/绑定能力验证。

能力只影响本次采用的执行方式，不扩大权限。初次建立工作区时按实际可用能力及既有授权选择原生或 Git 降级；已有工作区先恢复其管理方式与运行事实。某个必需操作不受当前宿主支持时，冻结依赖它的操作并说明准确缺口，不开始半套工作后再偷偷切换会话或复制半成品。

## 先核对实际根

先消费现有 resources/notes 中的工作区管理方式及恢复入口。宿主原生管理的工作区沿宿主恢复；Git 降级创建的工作区沿普通会话的实际 cwd 恢复，不自动再次 EnterWorktree 接管。管理方式未知时核对创建回执和宿主上下文，不仅凭 `.claude/worktrees` 或 `.worktrees` 路径猜测。当前已有执行者或原生隔离拒绝时保全状态，由协调器按既有授权完成明确交接，不能自动移出该会话。

分别运行 `pwd`、`git rev-parse --show-toplevel`、`git branch --show-current`，将实际结果与计划/claim 的 worktree、branch 对照。派发消息中的路径和父线程 cwd 都不是子线程已切换目录的证明。

工具支持 cwd 时逐次传入已核对的目标；只有宿主支持切换工作区时才切换。宿主固定在其他工作区时报告具体限制，保留 claim 与现场，由协调器按恢复协议处理，不能先在错误目录 bind，也不能临时把业务写到集成区。

项目文件相对于实际项目根，插件规则相对于实际插件根，其他 worktree 的证据使用各自已核实的绝对路径。存在 CodeGraph 索引且项目要求优先使用时遵从；否则先用 Glob 或 `rg --files` 定位实际文件，再 Read。出现 `File does not exist` 时核对文件名、根目录、Git 检出及文件是否已创建；仅凭这条消息不能认定权限不足。

## 选择宿主可以检查的操作

- 局部文本、JSON、配置和源码编辑先 Read，再用 Edit/Write 或宿主等效文件工具精确修改，随后读回目标字段与无关内容。依然遵守 writes、绑定、文件工具自身的权限检查和适用的原子写入契约；普通文件编辑不能代替要求原子更新的 progress/锁操作。
- Git 命令在已验证的工作区内独立执行，路径和参数写明确。不要把目录切换、动态拼参、Git 和其他文件写入藏在同一内联程序中。
- 项目已有脚本及必要的数据处理仍按批准入口运行；不要为了执行一条被拒绝的命令而增加临时脚本、额外解释器或编码层。某个复杂命令被拒绝不代表所有 Python、Node 或 heredoc 都不可用。
- RTK 等包装遵从用户/项目约定。怀疑包装导致拒绝时，只在已有授权下对同一操作做无包装对照，核对 hook 是否实际改写命令；仅在提示词里省略 `rtk` 不足以证明没有自动包装。试验保持原工作区与宿主安全检查，不改全局配置。

### 查询与执行分阶段

所有依赖 Git 查询结果的批处理，都按下面顺序生成工具调用；格式化、测试选择、代码生成和打包只是在消费结果时使用不同工具：

1. 在已核对的工作区独立调用 Git，取得实际需要的数据。文件列表优先保留 NUL 边界，不按空格拆路径；机器消费的输出保持原始语义，不硬编码一个可选包装器。
2. 代理消费回执，按本票授权、文件存在性、扩展名或其他业务条件得到精确输入集合。写入动作与 writes 求交集；排除规则来自任务，不把某个项目的生成文件命名推广为全局规则。空集合跳过，不扩大到整目录。
3. 以字面参数发起下一次工具调用，逐个引用路径，核对该工具的 cwd 与相对路径基准。名单过长可分批；不得把查询、拼参、目录切换和写入重新藏进同一内联解释器、命令替换或动态执行链。
4. 核对执行状态、实际产物及变更范围，保留原件；工具成功不代替任务的行为验证。

要求锁内原子提交的协议段不能为了满足上述形式而拆散：使用项目已有、获批且当前宿主支持的稳定入口，执行前确认其能力；没有可用入口就报告该协议的兼容性缺口。若任何独立步骤被宿主拒绝，按下节保留原始拒绝和现场。

## 区分失败位置

| 回执 | 先确认 | 处理 |
|---|---|---|
| 文件不存在 | 实际文件名、项目根和检出版本 | 定位真实文件；确认缺失时报告缺口 |
| `This session is isolated in the worktree … Refusing to run it` | 宿主在程序执行前拒绝的完整理由、实际命令与包装 | 保留拒绝；采用宿主允许的原生操作或明确的简单命令；无法满足时冻结依赖它的工作 |
| `EACCES` / `EPERM` | 哪个程序访问哪个路径时失败 | 按具体权限来源处理，不凭相似症状 chmod 或扩大授权 |
| `task binding: …` | task-binding 是否真正运行、authority/claim/范围哪项无效 | 沿绑定与恢复协议处理，不能关闭守卫或手写回执 |

同一被拒绝操作不能通过改名、重新编码、换解释器、放宽安全设置或转到其他会话偷偷执行。明确报告自动审批拒绝的操作和原因；当前授权中可独立推进的部分继续完成，不把局部阻塞变成整项停摆。

## 绑定与恢复的证据

绑定步骤仍以 [plan-format](../../writing-plans/references/plan-format.md#绑定与激活唯一定义点) 为准；保留原 CLI、authority、工作区、精确写集和回执校验。宿主拒绝 `bind` 时，不能把这条命令记为已经执行，也不能把拒绝当作 `no active task receipt`。

发现已有回执时用 `inspect` 核对身份及有效性，记录可取得的建立来源。操作者手动执行后得到的有效回执只证明当前绑定可用，不证明 agent 的自动绑定已恢复。恢复同一任务可消费有效回执，仍需按任务规则核对现场；没有有效绑定时冻结依赖绑定的写入，保留半成品与原件，不因这次绑定拒绝自动 clear、改 claim、搬代码或重建已有 worktree。

兼容性结论限定宿主版本和实测入口。2026-10-27 对 Claude Code 2.1.311 的隔离会话对照中，RTK hook 开启/关闭时 `bind` 参数均被误判为执行字符串的命令，完整 JSON 内联修改均被拒绝，简化 heredoc 均成功。该结果要求逐条验证实际命令；它不是取消隔离或将任意脚本判为安全的依据。完整恢复须验证 agent 自行绑定、编辑与读回，并继续拒绝无效 authority 和越界操作。
