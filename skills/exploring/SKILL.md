# 探索模式（Exploring）

开始前先读 [clarifying 的提问规则](../clarifying/SKILL.md)；本次会话已经读过就不用再读。

陪用户想清楚一件还没决定做不做的事：读代码、比较方向、画图说明。不要求固定步骤，也不要求得出结论。

<HARD-GATE>
探索期间只读代码、讨论、画图，不写生产代码，不搭正式脚手架。允许的写入只有两种：比较界面方案时按原型契约生成隔离的 HTML 原型；用户同意后做下面的受控实验。要交付的功能不能当成实验来写。
用户要求直接实施，或你判断该动手改代码时，当轮就提议转 requirement-analysis，不必等方案比较完；用户没同意就继续探索。
探索笔记先提议，用户同意后再保存。
</HARD-GATE>

## 受控实验（spike）

只在一个问题必须运行代码才能回答、且答案会影响决定时做。它属于 [test-driven-development](../test-driven-development/SKILL.md) 例外清单里的一次性原型。先告诉用户要回答的问题、要写的文件、要用的资源，同意后再动手；同一问题、同一范围内不再重复问，范围扩大了重新问。用户同意过用独立原型回答这个问题、而文件已经不在时，可以重建并运行，并说明是新建的。

- 实验代码放进名字带 spike 或 prototype 的独立文件，顶部用注释写明要回答的问题，例如 `// 实验问题：<必须运行才能回答的问题>`。先确认它不会被构建打进生产产物，隔离不了就换位置或停下。
- 状态默认放内存。问题本身与存储有关时，用用户同意的独立临时库或目录，不碰真实业务数据；读写或删除前核对最终的绝对路径确实在同意过的位置。
- 不写正式测试，不打磨，不抽象。
- 创建持久资源时当场记下标识和清理方法；只清理本次创建的。
- 结束时报告：问题、文件和资源位置、实际运行的命令和输出、结论和没证实的部分、哪些保留哪些已清理。跑不通只说明这次没跑通。实验代码不直接并入生产提交；转 requirement-analysis 时只带结论和出处。

## 怎么聊

本代理自己收到 `spec-dev collaboration: enabled` 时，另按 [模型协作增强](../requirement-analysis/references/model-collaboration.md) 执行；它不把探索变成实施，也不要求探索得出方案。

- 先读相关代码和文档，再开口。项目的词汇表和以前的决定按 [context-reuse.md](../requirement-analysis/references/context-reuse.md) 查。开场简短说明你依据的假设和还缺的信息；没读到的历史数字或决定就说不知道。
- 目标、范围不清楚时先按 clarifying 的提问规则问清；清楚了就直接探索。
- 平时多给方向让用户挑，不连续追问。只有遇到互斥、不能同时探、用户不选就没法继续的选择时，才一次一题地问，问完回到开放讨论。
- 能画图说清的就画（架构草图、状态机、数据流、对比表）。需要比较真实界面时按 [原型契约](../visual-preview/references/ui-prototype-contract.md) 出 HTML 原型，用户的反馈按 [界面澄清](../clarifying/references/ui-clarification.md) 处理。项目还没有前端时，为画原型选的技术栈只算本次探索的假设。

## 外部事实研究

核查第三方依赖、服务或标准的能力和版本时，按 requirement-analysis 的 [外部研究 brief](../requirement-analysis/references/external-research-brief.md) 做，自己查和派子代理查都一样。放在本地的第三方材料（离线包、源码副本）也按外部事实对待。

## 可选的后台调研

范围明确的只读问题可以派子代理在后台查，主线程继续聊不依赖这个结果的部分；要用到结果之前，先核对它的来源、查了哪些范围、还缺什么。派发时给出 requirement-analysis 的 [探索 brief](../requirement-analysis/references/explorer-brief.md) 或外部研究 brief 的绝对路径，写明主题范围、完成条件和只读要求。失败先缩小范围重试一次，再失败主线程接管；没有子代理能力时自己查。子代理只调查，不写实现、不保存笔记、不替用户做决定。

## 探索笔记（可选，先提议）

得出有价值的结论时，提议保存到 `.spec-dev/explorations/<topic>.md`，用户同意再写。内容从简：问题、关键发现（附代码证据）、比较过的选项和取舍、已排除的选项、还没定的问题。已排除的选项按 [context-reuse.md](../requirement-analysis/references/context-reuse.md) 记下概念、理由、谁决定的、适用条件，与没定的问题分开写。结论是“不值得做”也可以记。用户不要就留在对话里。

## 怎么结束

没有必须达成的结局，三种都可以：

1. **转正式设计**：能说清还要回答哪个问题才能交付时，就可以提议「要转成正式设计吗？」，不必先选定方案，方案比较是 requirement-analysis 的事。用户同意后调用 requirement-analysis，把探索结论和已保存的笔记交给它的第 1 步，探索过的不重做；用户没同意就继续探索。
2. **到此为止**：用户已经得到想要的答案。
3. **以后再聊**：提议保存一份探索笔记，方便下次接着聊。

结束时可以给一段小结：想清楚了什么、有哪些方向、还有什么没定。

## 被实施流程调回时

executing-plans 执行中卡住时（计划与接口对不上、设计可能有错），可以回到探索模式把这个子问题想清楚，再按下表把结论写回对应的文档，回去继续执行：

| 得出的结论 | 写回哪里 |
|---|---|
| 设计决策变了 | 修订 spec（须让用户 review 修订） |
| 范围变了 | 回 requirement-analysis 走对应阶段 |
| 冒出新任务 | 补进 plan（对齐任务结构） |
| 假设被推翻 | 修正对应文档并记录 |

## 环境限制

受控实验需要能运行命令；做不到就向用户说明。其余按文首的宿主适配处理。
