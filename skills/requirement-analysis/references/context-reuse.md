# 概念、否决与共享术语复用

本文件是路由前双查、概念级否决记录和仓库共享术语的单点定义。入口只给用途摘要与指针，不复制规则。

这里的仓库指用户项目：项目 `.spec-dev/` 及其产物引用在用户项目中解析，不在插件规则目录中解析。先核实用户项目根，不能把规则文件所在仓库当成用户产物根。

## 路由前双查

RA、quick-fix 与 triage 提议路线前，按当前问题限定范围：先用领域概念及已确认别名核查已有实现，再查相关 .spec-dev/explorations/ 笔记中的历史否决。已有实现报告位置和适用边界，不能写成否决；历史否决报告原理由、用户决定来源及适用条件。条件改变、新证据或用户改判可重新讨论，命中记录不自动拒绝请求。

先读适用域相关的 .spec-dev/glossary.md（存在时）帮助按概念查询。结果保留概念、检索范围、实现指针、相关否决及未核查范围。没有仓库或文件时如实说明，读取失败不当作查无记录，不要求全仓穷举，不为双查创建文件。显式 skill 选择及同范围已有决定直接消费，不重复路由确认；原有建议式路由不变。

复述旧值或旧决定前先取得对应记录；把历史事实、本轮给定事实和待查假设分开，不能用当前预算等不同角色的数字补出旧报价。

历史排除与本轮重开分别核对：
- **历史排除背景**：原记录的理由和适用条件描述当时为何排除。按原义转述，不将这些字段改称记录设定的“重新讨论条件”，也不把原条件满足写成才可或才需重审的前提。
- **本轮重新讨论**：依据用户当前请求或新事实推进；用户明确要求重开时，旧条件未变也直接继续讨论。条件变化或新证据同样可以成为讨论依据，不把当年的排除决定当作永久禁谈。

最终结论与交接中的历史段落也按这两个不同问题核对：保留当时的排除背景，不把本轮的建议或新条件归于旧记录。重新讨论本身不等于批准实施。

## 否决记录

exploring/clarifying 获准保存笔记时，将已排除概念单列为「已排除选项」：概念、理由、用户决定来源、适用条件。未决问题仍单列；条件变化时追加重开说明，保留原决定，不覆盖历史。不新建否决知识库目录，不把已实现能力记成否决。未获保存授权只在对话保留。

## 共享术语

进入相关讨论时，RA、quick-fix、triage、exploring 和 clarifying 读取适用的仓库 .spec-dev/glossary.md。只收跨特性复用的项目专有概念，不收通用编程术语；本特性局部概念留在 spec。记录形状：

- **规范名**：一两句定义。_Avoid_：别名（无则写无）。适用域：具体领域。来源：对应获批设计/用户裁决的可恢复指针。

同名不同义先展示定义、域和来源，逐题由用户裁决；跨域可并存，不强行全局唯一命名。glossary 与现行 active spec/Accepted ADR 矛盾时点明冲突，沿现有契约姿态及取代流程处理；词汇表不自动推翻合同、不触发全仓旧术语替换，也不参与守卫解析。

RA 在完整设计获批后的 spec 落盘阶段才懒创建/更新 glossary，和 spec 同次范围提交；首次没有共享术语就不建空文件，局部术语留 spec。独立 exploring/clarifying 的术语决定先留在对话，只有选择原有保存出口或已明确授权更新词汇表才写文件。triage 始终零落盘。保存失败报告错误及待保存内容，不宣称成功。

保存内容限于已批准设计。实际写入或提交前，以将保存的最终 spec/glossary 正文及 frontmatter 为对象，逐项对照本轮批准来源：核对新增行为义务、接口结果、已确认决策和取代声明，不只核对文件名、格式或提交范围。仅术语的设计只记录定义、适用域、Avoid、来源及必要概念说明，不把模板空节补成运行时 SHALL、实现策略或 supersedes。尚未获批的行为留待后续设计，不固定在本次稿件；共享记录不扩大原设计范围。

讨论备选方案时区分现行定义与拟议变化：同名状态或概念若改变了成立条件、适用域或保证，明确指出差异并保持待裁决，不能仅因名称相同就称为保留现有语义。提出新方案本身不改写旧契约。

后续阶段消费既有定义及决定来源；没有新冲突不重复确认。来源失效保留缺口，不自行补造决定。
