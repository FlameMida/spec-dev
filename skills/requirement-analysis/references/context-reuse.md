# 已有实现、历史否决与共享术语

开始前怎么查已有实现和历史否决、否决记录怎么写、共享术语怎么读，都只在本文件定义；其他文件链接到这里。

这里说的仓库是用户的项目：`.spec-dev/` 和其中引用的路径都相对用户项目的根目录，不是本插件所在的目录。先确认用户项目的根目录在哪。

## 开始前查两件事

requirement-analysis、quick-fix 和 triage 在建议走哪条流程之前，围绕当前问题查：

1. **是否已有实现。** 用领域概念和它的别名搜代码；有 `.spec-dev/glossary.md` 时先读它来确定用词。找到就报告位置和适用范围。已有实现不是否决，不要写成否决。
2. **以前是否否决过。** 查 `.spec-dev/explorations/` 里相关笔记的“已排除选项”。找到就报告当时的理由、谁决定的、适用条件。

以前否决过不代表现在不能做：用户要求重新讨论，或条件、证据变了，就照常讨论；同意重新讨论也不等于批准实施。转述旧记录时保持原意，把“当时为什么否决”和“现在为什么重提”分开写，最终结论和交接材料里也一样。引用以前的数字或决定前，先找到原记录；历史记录里的事实、本轮给出的事实和还没查证的假设分开写。

结果里写明：查的是什么概念、查了哪些范围、实现在哪、相关的否决记录、哪些没查。没查到就说没查到，读取失败就说读取失败，项目不是 git 仓库或没有这些文件也照实说。不必全仓搜索，也不为此新建文件。用户已经点名用哪个 skill，或同一范围已经有决定时，不再确认路线。

## 否决记录

exploring 或 clarifying 获准保存笔记时，把已排除的概念单列为「已排除选项」，每条写：概念、理由、谁决定的、适用条件。还没定的问题另列。条件变了要重新讨论时，在原记录后追加说明，原决定保留。否决记录就写在探索笔记里，不另建目录；已经实现的能力不记成否决。没有获准保存时只留在对话里。

## 共享术语

讨论前读相关领域的 `.spec-dev/glossary.md`。它放在哪、怎么写、什么时候可以保存、与 spec 冲突怎么办，都在 [跨技能文档规范](document-conventions.md) 里；要读写术语或 ADR 之前先读那份全文，本次会话读过就不用再读。只在一个特性里用的术语留在那份 spec 里。已经批准过的术语直接用，换了会话也不重问。
