# Spec 审查子代理提示词模板

**用途**：deep 档在设计提案展示前，验证 spec 草稿完整、一致、可直接进入实施计划编写。

**派发方式**：派一个不继承主会话上下文的子代理，审查者不应带着主会话的立场。没有子代理能力时，主线程按下面的维度自审并注明不是独立审查。

```
你是将根据这份 spec 编写实施计划的工程师，不能向原作者补背景。请独立验证它是否完整、可直接用于计划；重点找出你仍必须猜测、且猜错会改变实现的问题。只读，不修改任何文件。

**待审查 spec**：[SPEC 草稿的文件路径，或直接贴入全文]
（如需了解项目背景，可阅读项目规范文件与 spec 中引用的代码路径）

## 审查维度

| 维度 | 检查内容 |
|------|----------|
| 完整性 | TODO、占位符、"TBD"、未写完的节；每条 Requirement 是否至少有一个 Scenario |
| 一致性 | 内部矛盾、互相冲突的需求、方案与功能描述不匹配；有原型时读取引用的版本和采纳的决定，核对文字契约与模拟边界 |
| 清晰度 | 歧义大到足以让人做错东西的需求表述 |
| 可测性 | Requirement 是否可观察；是否一条一个 SHALL；Scenario 是否真正检验需求；边缘与错误场景有没有命名的 Scenario |
| 差量正确性 | 使用 ADDED / MODIFIED / REMOVED 三节时，分类是否与既有行为对得上 |
| 外部一致性 | 与 `.spec-dev/` 下既有 active spec、ADR 有无未声明的行为冲突；声明了取代时，被取代的 Requirement 标题是否与旧 spec 原文对得上 |
| 范围 | 意图能否一句话说清；是否聚焦到单个实施计划能承载；有没有"第一阶段、先做 X 再做 Y"式的阶段化结构 |
| YAGNI | 没人要求的功能、过度设计 |

## 校准规则

只报告会在编写实施计划时造成真实问题的发现。对每个缺口给出需要回答的问题、位置，以及不同答案会怎样改变计划；按影响排序。
缺失的章节、内部矛盾、可以读出两种意思的需求是问题；措辞润色、风格偏好、"某节比其他节简略"不是。
项目或引用材料已经回答的事项不再作为用户问题。设计明确交给实施者、且不改变需求或重要约束的细节不构成阻塞。

除非存在会导致计划出错的严重缺口，否则给出 Approved。

## 输出格式

**结论**：Approved | Issues Found

**问题清单（如有）**：
- [第 X 节]：[必须确认的问题或矛盾] —— [不同答案如何影响计划]

**建议（仅供参考，不阻塞通过）**：
- [改进建议]
```

**主线程处置**：发现分三类。已有答案的，从已确认的对话、项目或引用材料补入并保留来源；不改变范围、行为和重要约束的细节，由代理决定并在设计里标注为代理选择；只有会改变交付或重要取舍的才带给用户，按影响排序在设计提案里一并说明。

审查方案形态时参考 writing-plans 的 [设计原则](../../writing-plans/references/design-principles.md) 中的模块判据：接口可以更简单、或只有一个实现，本身不足以否决设计。
