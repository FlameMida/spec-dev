# 模式切换与任务恢复

> 阅读时机：首次编排、任务边界切换、会话恢复或处理集成组之前；上下文压缩后从磁盘重新读取适用规则，不能只凭摘要恢复。

### 默认并发与任务边界切换

执行授权已确认且用户没有明确串行限制时，分文件计划只要有合法 parallel 声明、至少一张可派发票及可核验的写入/资源边界，就默认进入并发编排；不要求至少两条独立链，也不增加并发选择门。共同前置未完成不阻止初始化，实际派发仍等依赖 completed。只有一票 ready、纯依赖链或共享资源排他时逐票运行；有互不冲突的多票 ready 时并发补位。

首次编排、切换准备或并发恢复之前读取 [并发执行模式](parallel-execution.md)；模型声明、锁、认领、持续补位与接收由该 reference 及其按需引用定义。用户明确要求主线程串行时遵从并沿现有 notes 保存偏好及来源，普通「继续」不撤销该限制。缺声明、无可派发票或平台无法可靠隔离时说明原因，由主线程沿已授权范围串行执行；声明损坏、契约缺失或恢复事实不明仍先处理具体阻塞，不以降级绕过校验。单纯容量暂时不足就等待，不撤销活跃 claim。

已提交 execution.mode=parallel 时先恢复原集成工作区、锁与 claim，不重新初始化。存量无 execution 的进度不等于用户要求串行：先完成当前票/活动组，再在干净且可核验的任务边界按下述协议激活默认并发；已有明确串行选择或冻结单文件计划继续串行。本 skill 是唯一执行入口；仅有文档链接、计划文件或 skill 自动加载仍不构成执行授权。

执行摘要消费 index 的「并发准备」说明与四列导航：指出共同前置、可重叠的链及主线程专属票；任务编号不制造依赖，同批也不是完成屏障。spec 的共享契约、接口块或独立验证条件缺失时报告具体缺口，按原偏差纪律修订受影响计划，不在执行入口临时拆票或删依赖。准备方法只在 writing-plans 的 [并发准备](../../writing-plans/references/parallel-readiness.md) 定义。说明默认调度和适用限制即可，已有执行授权不重复询问开始或并发许可。

默认策略在串行任务边界生效，或用户在票中途要求切换时，按并发激活协议保存 request_id 及来源（执行授权与默认规则，或用户切换请求）到 notes 并单独提交，不能把默认决策伪写为用户说过“并发”。当前票由主线程继续完成；其完成检查点干净可核验后，复用原隔离 worktree 激活，不重做 T00。原始审查基线保持不变；模型表、锁与检查点顺序由 reference 定义。条件不足继续已授权串行，缺声明不自动改计划；恢复不丢失已保存的决定或重派半成品。

并发分支完成全部实施票集成后回到本 skill 阶段 4—6。只有该分支的 implementer 可以写获准代码，其他探索/审查子代理继续只读。存量单文件按现有冻结分支执行，不新增并发元数据。

**恢复入口**：会话开始即发现未完成的 progress.yaml（或单文件计划有未勾选步骤）且用户要求继续 → 走「渐进加载与断点恢复」节的恢复流程（校验一致性 → ready 任务续跑），不从任务 0 重来。


### 渐进加载与断点恢复（分文件形态＝全部新计划）

- 启动只读：`index.md` + `progress.yaml`（+ 同特性目录 spec）。**不读任何 tasks/ 正文**。
- 执行 TN 时只读：`tasks/TN.md` + 导航表中 TN 依赖行的「产出接口」列。不提前读无关后继任务正文。
- 普通任务完成条件（全部满足才置 completed）：依赖全 completed、适用 TDD/纯重构步骤完成、测试通过、commit 可解析、接口块与导航表一致、progress.yaml 已原子更新并随任务提交。含 claim 的票还须与 completed 同次在 notes 保存二元退役处置，接收后执行清理/有因保留复查；物理删除独立留回执，不因清理失败回退业务状态。含组成员/验证票的完成与 ready 由 integration-groups 定义；本票操作已保存不等于 completed。
- 偏差处理沿用主文件三级纪律；契约级偏差冻结受影响后继（导航表依赖闭包），修订 index 接口行与相关任务文件后再继续。

**恢复执行（resume）**——检测到 `progress.yaml` 存在且有非 completed 任务时：
1. 校验一致性：集成工作区及仍活跃认领的 worktree/分支存在，completed 各任务的 commit 可 `git cat-file -e` 解析，progress 引用的任务文件都存在。completed 但未退役者沿票级协议补处置并复查；已删除未销账者须凭删除前处置、存活归档与真实删除回执补账，不凭目录消失推定成功。已按台账合法退役的 implementer 工作区沿 [票级退役](parallel-result-integration.md#票级-worktree-退役) 核对保留提交、证据及清理回执，不要求目录或分支仍存在，不重建它来重跑 completed。current 的 in_progress/blocked 不要求完成 SHA，已有实现提交须核验但不据此自动标 completed。缺失且无合法退役依据 → 停下向用户报告不一致，不猜测继续。
2. 普通串行先恢复 current：in_progress 续接，blocked 先处理阻塞；没有当前票才取下一 ready 任务（依赖全 completed 的最小编号 pending）；组分支消费 plan-state 的 ready_tasks 并按 integration-groups 恢复。同前只读该任务文件与依赖接口行。
3. 恢复不无条件重跑 completed 任务；核验原件、版本与检查范围，缺口或变更按 test-strategy 补验，独立 F 保留全量安全网。

**存量单文件的轻量恢复（兼容分支）**：单文件计划无 progress.yaml；先核对已有绑定、明确 task key 及授权/执行记录，定位本次任务。未勾选步骤只提供候选，不能把首项当授权；多个未完成任务且无法唯一定位时报告具体缺口，不猜测。复选框与实际提交、验证原件逐项对照；提交存在不代表验证和状态保存已完成。补写当前/未执行范围后，按稳定 TNN 绑定，保留原历史。

## 集成组分支

涉及集成组的进入、组员检查失败、调度或恢复时，先读 [integration-groups.md](integration-groups.md)，再应用该分支；不要先套普通票的 ready/completed 规则。进入组前检查的是整组全部外部前置，组首单票 ready 不足以开工。组内意外局部失败使成员与组 blocked；修复后成员恢复待验，全部成员待验后才执行组验证。恢复时先处理尚未待验的成员，不能仅因当前票已待验就直接跳到验证。

含组的 v2 先使用 plan-index 和 plan-state 协议检查，按 [integration-groups.md](integration-groups.md) 执行主线程独占、待验、组验证与恢复。无组 v1/旧单文件保持原分支。每个状态边界以已提交检查点为准，组内 awaiting_verification 只允许本组显式依赖消费；组外等验证票 completed。组验证是阶段 3 的普通执行类型，不与阶段 4 的 acceptance-qa 任务混淆。
