# 执行实施计划

<HARD-GATE>
全部实施任务完成后，未经用户当次明确同意，不得运行全量或回归测试套件、E2E、浏览器或性能验收，也不得加载 acceptance-qa。任务内的目标测试与项目已有的快检不受此限。拿不到用户回复（无人值守、非交互运行）按未同意处理。计划头部「收尾预先决定」里用户写明的选择等同于同意。
</HARD-GATE>

流程只有四段：载入并确认，建工作区，任务循环，收尾。主线程写实现代码，子代理只做只读审查。计划文件是唯一的事实源。

## 1. 载入并确认

1. 读计划全文和同特性目录的 spec（默认 `.spec-dev/YYYY-MM-DD-NN-<feature>/plan/<feature>-plan.md`；用户另有指定时按实际入口读取用户指定位置）。计划头部写明没有 spec 时只读计划：头部的验收标准承担 Requirement 与 Scenario 的角色，后文提到 spec 的地方都按它处理。
2. 批判性审阅：步骤有歧义、接口互相矛盾、与代码现状不符的地方，先向用户提出，不带着疑虑开工。
3. 确认开始。用户本轮已明确要求执行，或在 writing-plans 交接时已批准计划，都不重复问；否则给出任务数、依赖概况和将使用的分支名，等用户点头。
4. 记下计划头部的「收尾预先决定」。

## 2. 建工作区

按 using-git-worktrees skill 建立或复用隔离工作区，分支名对齐计划（如 `plan/<特性目录名>`），装好依赖。开工前不运行任何测试。把工作区路径和分支写进计划的「执行记录」并提交。

用户或项目声明原地工作，或无法建立隔离且用户同意时，原地执行并在执行记录里注明。

**spec 启用了漂移守卫时**（frontmatter 填了 `covers`）：实施期间 spec 保持 `draft`，守卫只看 `active`，所以任务提交不会被拦。特性分支的第一次提交处理受影响的旧 spec：

- 被本 spec 完全取代的旧 spec 置为 `superseded` 并填 `superseded_by`。
- 被部分取代、或本次直接修订的 active spec 暂时改回 `draft`，被取代的 Requirement 标题下加一行 Superseded 标注。

这些改动只在特性分支上，主分支合并前不受影响。没有 frontmatter 的 spec 不参与守卫，跳过本段。

## 3. 任务循环

按导航表的真实依赖逐个执行，同样就绪的取编号最小的。每个任务按下面六条做：

1. **重读**。开工先重读计划头部（目标、非目标与全局约束）、本任务、所依赖任务的产出接口。上下文被压缩或换了会话，同样先重读再动手，不凭记忆继续。
2. **只做任务写明的事**。任务外的发现（旁边的 bug、更好的写法、可以顺手改的东西）记入「执行记录」的任务外发现，不在本任务里处理。
3. **按步骤 TDD**。遵循 test-driven-development skill：测试先红后绿，红必须是目标断言失败。只运行本任务的目标测试和计划写明的快检，不在任务内跑受影响范围或全量。
4. **测试锁定**。已经提交的测试断言不得修改、删除或跳过。确实要动（测试本身写错、契约已获批变更）时按契约级偏差停下来问。自检时用 `git diff <任务起点>..HEAD -- <测试文件>` 核对。
5. **提交并勾选**。一个任务一次提交（`feat(T03): ...`），同一次提交里勾选本任务的复选框并填「红转绿记录」。
6. **自检两问**。对照本任务重读 diff：有没有多做或少做？本任务产出的接口与计划的接口块一致吗？发现就地修正并补提交。这里不找 bug、不查风格，那是收尾审查的事。

**连续执行**。任务之间不停下来汇报或请示，用户已经批准过计划；回答用户的进度询问后继续做。只在三种情况停下：无法自行解除的阻塞、真正挡住前进的歧义、全部任务完成。因阻塞或歧义停下时，把卡在哪一步、实际运行的命令和关键输出写进执行记录并提交，让用户不必重现就能判断。

**偏差分三档处理**：

- 小偏差（路径笔误、意图明确的遗漏）：就地修正，记入执行记录。
- 契约级偏差（接口或数据结构与计划不符且影响后续任务、需要改已提交的测试断言、触及其他特性的 spec）：停下向用户确认方向，不猜着改。
- 意图级偏差（要做的已经是另一件事，或范围明显膨胀）：停下，建议收尾当前计划，新工作另走 requirement-analysis。

**例外与纯重构**。跳过测试只沿 test-driven-development 的例外清单，不凭"这个简单"豁免。纯重构任务用前后都通过的行为测试保护，不伪造失败。

**遇到与本任务无关的失败用例**。只把这一个用例在分支起点的提交上复跑一次（可以用临时的 detached worktree）：起点就失败的记入执行记录后继续，起点通过的是本次回归，必须修。

**恢复**。恢复只认计划文件和 git log：读复选框与执行记录，核对工作区、分支和最近的提交，从第一个未完成的任务继续。已勾选且有提交的任务不重做；全部勾选但还没交付的计划直接进入收尾。勾选与提交对不上时（勾了没提交，或提交了没勾），不凭其中一方认定完成：重跑该任务的目标测试，通过后补齐另一方并记入执行记录。工作区里有未提交的改动时，先判断它属于哪个任务，不丢弃。无法确定进行到哪个任务时，向用户报告具体缺口，不猜。

## 4. 收尾

全部任务完成后按顺序做下面五件事，其中只有询问门会停下来等用户。

### 审查

派一个只读子代理审查本计划的全部变更（`git diff <分支起点>...HEAD`）。派发词里给出 [审查 brief](references/reviewer-brief.md) 的绝对路径、spec 与计划路径、diff 范围，要求它先读 brief、只读不改。变更跨多个模块、风险面大，或用户要求彻底时派两个：一个看正确性与 spec 符合性，一个看质量与项目规范。没有子代理能力时，主线程按 brief 换视角复查，并在总结里标注"非独立审查"。

审查者不运行全量测试。审查返回后先确认工作区没有被改动。高、中严重性的发现逐条读代码核实：成立的行为缺陷先写复现测试再修，不成立的记下理由。修复限于本计划范围，超出范围的交用户决定。

### 摘要与对账

向用户给出完成的任务、变更文件、审查发现及处置、偏差和任务外发现，以及 Requirement 对账表：逐条 Requirement 对应实现它的任务与测试，标明已交付或未交付。未交付的不得含糊带过。

### 询问门

一次问清三件事。问之前按实际改动给出推荐和理由：改了页面就推荐看页面，改了接口就推荐调接口，改了数据迁移就推荐演练迁移。

1. **回归**：不跑 / 只跑受影响范围 / 全量。走 PR 且项目有 CI 时，可以选择把全量交给 CI。
2. **验收**：此时从 spec 的 Scenario 生成验收清单，每行写行为、怎么看、预期结果。逐项由用户选：自己验（给出可复制的命令或步骤）、代验（并排给出预期与实际的原始输出或截图，不只报通过）、不验。
3. **交付**：本地合并 / PR / 保留分支。

「收尾预先决定」已经写明的项不再问。拿不到回复时按未同意处理：不跑回归和验收，分支保留不合并，输出总结后停止。用户没选的项不执行，并在总结里如实写"未执行"。

### 按选择执行

- 回归里本次引入的失败必须修，先写复现测试；判定为既有失败的列给用户。修复后只重跑受影响的部分。
- 代验需要 E2E、视觉、性能或诊断这类专项能力时，加载 acceptance-qa skill，范围限于用户选中的项。
- 未交付的 Requirement 由用户裁决补做、延后或放弃；延后与放弃在 spec 该 Requirement 标题下标注一行原因。

### 交付与总结

- 按用户的选择合并或开 PR，合并前确认工作区干净。推送、建 PR、合并各自需要用户授权，已经给过的不重复问。
- spec 启用了漂移守卫时，在交付提交里把 `status` 翻为 `active`，开工时暂时改回 draft 的旧 spec 一并翻回。
- 本计划属于某 roadmap 的子项目时，把对应行置为 `delivered` 并提交，提示依赖已满足的下一个子项目。
- 清理自己创建的工作区和持久资源（容器、测试库、临时目录），不是自己创建的不动。用户选择保留分支时不清理工作区。
- 输出总结：成果、对账计数、测试与审查情况、偏差、未执行项、后续建议。

## Red Flags

- "计划有点问题，我猜着改吧" → 契约级偏差停下问用户。
- "这个任务简单，跳过测试" → 只沿 test-driven-development 的例外清单。
- "测试过不了，改一下断言" → 测试锁定，改已提交的断言要先问。
- "都做完了，顺手把全量跑一遍" → 回归和验收先问后做。
- "顺手把旁边的问题修了" → 记入任务外发现。
- "每完成一个任务汇报一下" → 连续执行，别打断用户。
- "自己写的代码自己看一遍就行" → 有子代理能力就派独立审查。
- "没做完的 Requirement 总结里一笔带过" → 对账逐条标明，由用户裁决。

## 旧格式计划

执行早期版本生成的计划时按下表处理，不改写计划里的历史记录：

| 计划里的内容 | 现在的处理 |
|---|---|
| 任务 0（隔离工作区） | 只做隔离和装依赖，跳过其中的基线测试步骤 |
| 独立 final 验证任务、验收任务 | 到达时停下，按询问门先问 |
| 最终任务（合并与清理） | 按询问门的交付选择执行 |
| scopes 块，bind、inspect、clear 步骤 | 跳过 |
| spec 已是 active 且填了 covers | 在特性分支上改回 draft，交付时再翻 active |
