# 澄清纪律（Clarifying）

沿决策树一次一题，把一个想法、计划或决定磨到共识态。**事实是你的活，决策是用户的**——环境能回答的自己查，需要裁决的逐题交给用户，具体取舍附上推荐及理由。

**纪律定义以本 skill 为准**：exploring、requirement-analysis、quick-fix 和 visual-preview 按被引用模式消费；引用方文本与本文冲突时以本文为准。涉及原型时读取 [通用澄清与界面原型澄清](references/ui-clarification.md)，两者按实际未知切换，已决事项不重问，不机械执行两轮。

相关术语与历史否决按 [context-reuse.md](../requirement-analysis/references/context-reuse.md) 读取并处理冲突；保存仍沿本角色已有出口与授权，不自动建立知识文件。

## 两种角色

| 角色 | 进入方式 | 流程控制权 | 终点 |
|------|---------|-----------|------|
| **被引用模式** | exploring / requirement-analysis / quick-fix / visual-preview 处理当前未知 | 引用方 | 澄清完成，控制权回引用方下一阶段——**不呈现共识摘要与三出口，不发开场声明** |
| **独立会话模式** | 用户直接调用 clarifying | 本 skill | 共识态 → 共识摘要 → 三出口 |

## 核心纪律（两种角色共用）

- **第 0 条·基于上下文披露**——第一题前先查已有材料，简要复述已知目标和相关事实，并说明本次仍依赖的假设、会改变方案的信息缺口及具体易错点。三类是内部检查维度，不是固定三段；仅呈现与当前决策相关的内容，不编造缺口、风险或占位段落。已有同范围披露直接复用，有新事实才更新。两种角色共用。
- **未决决策清单**——多个事项或存在依赖时，以陈述句显示当前范围的决策名、未决含义及依赖；单一问题直接问，不另列清单。裁决后移出未决区或标已决，新解锁项追加，显式挂起与已决分开。清单只展示进度，不变成批量问卷或持久状态机；被引用时只覆盖当前环节。
- **一次只问一个问题**——普通澄清等用户答复再问下一个。仅 requirement-analysis 的 [spec 审查补问](../requirement-analysis/references/spec-review.md) 可在规定边界内集中询问；不将该例外用于独立澄清、日常探索或 quick-fix。
- **按问题选择形式**——目标尚未成形时用开放问题让用户描述；已有具体范围或方案取舍时优先给 2-4 个互斥选项，**推荐项放首位并说明理由**。问题须接续已读事实或上轮回答；理由不明显时说明答案会改变什么。选项比较同一个决策维度，不为凑数量制造方案（Claude Code 用 `AskUserQuestion`；开放问题用对话直接问）。
- **范围扩展先二分**——当前分岔是“是否需要扩大现有边界”时，只问两个排他范围：保持当前边界，或必须扩展。范围选项只约定需要支持的对象或场景，不隐含选择尚未裁决的实现机制；例如先确认同机或多机，不能把共享文件系统或事务服务绑定到范围答案。可以说明可能的实现代价，但明确机制仍待选。扩展已包含原范围时不另列“两者都要”；多套实现等后续决策待范围裁决后另问。
- **最终消息核对**——相关假设、关键未知和具体风险已说明，问题能推进当前决策，不重复材料或用户已经回答的内容。选项互斥且每项只锁定当前决策；同一政策不能同时命中两项，也不把下游未决事项藏进选项。核对在内部完成，不增加固定栏目或批准门。
- **事实自查，决策交用户**——能由环境（代码库、文件系统、已有探索产物、工具）回答的事实性问题自己查证，绝不抛给用户；真正需要用户裁决的才带到对话
- **按决策依赖排序**——沿决策树逐支下行，上游决策未定时不问下游问题（如存储选型未定就不问索引设计），避免上游答案变化令下游澄清作废；同级可决项按重要性排序
- **裁决来源**——推荐、沉默和显式挂起不算回答；依赖决定的动作继续等待。可恢复上下文中同范围已有明确决定且无新冲突时直接消费，不能因清单或会话恢复重问。
- **委托范围**——用户明确交给代理的实现细节，可在现有约束内决定并标注为代理选择；未委托且会改变范围、行为或重要取舍的问题仍交用户。不得把默认值记为用户原话或扩大委托。
- **术语挑战**——用户用词模糊或一词多义时，当场提出规范术语请用户裁决，此后全程沿用
- **不编造问题**——没有疑点就明确说"已清晰、无需澄清"并收束；为走流程而提问和带着错误假设前进同样是浪费

## 独立会话模式

<HARD-GATE>
澄清会话只提问与查证，不实施：可以读文件、搜代码，但绝不编写生产代码、不搭脚手架、不执行实施动作。用户在会话中要求直接实施时，引导走出口 1 转入对应主流程 skill。
</HARD-GATE>

1. **开场**：声明「我正在使用 clarifying skill，逐题把这件事磨清楚。」无参数时先问一句"要磨清楚的是什么"。
2. **先探索后开题**：轻量查证（Grep/Glob/Read；Codex 下 `rg` + 文件阅读）能自答的事实，再开第一题。
3. **逐题下行**：按核心纪律沿决策树推进，直至**共识态**——所有决策支线要么已由用户裁决、要么被显式挂起为未决点，无静默假设。
4. **共识摘要**：呈现达成的理解 + 挂起的未决点。
5. **三出口**（提议制，用户选；除已有授权的原型设计产物外，未选前不自动落盘笔记）：
   - **转主流程**——按承诺状态、任务类型与设计空间建议 requirement-analysis（已承诺、有设计空间）、quick-fix（已承诺、无设计空间）或报告通道（已承诺的非开发交付，约定见 requirement-analysis 阶段 1 任务类型检查），经用户确认后进入；共识结论作为下游输入，**已裁决过的问题不在下游重问**
   - **就此结束**——共识留在对话里，零产物
   - **写入 md**——落盘 `.spec-dev/explorations/<topic>.md`（复用 exploring 的落盘约定，结构从轻：问题、关键结论、未决点），改天转正式流程时由 requirement-analysis 阶段 1 作为输入消费

## 与 exploring 的分界

分界是嵌套而非对立：exploring 默认发散，入口的必要目标澄清、关键分岔与原型反馈以被引用模式复用本 skill；当前问题清楚即返回探索，不强制每条支线收敛。

| | exploring | clarifying |
|---|-----------|------------|
| 姿态 | **发散**——开支线让用户挑方向 | **收敛**——沿决策树逼近共识 |
| 提问 | 问题自然涌现，不照脚本（关键分岔漏斗期除外） | 逐题下行，覆盖每条支线 |
| 终点 | 可以没有结论 | 共识态（或显式挂起） |
| 典型措辞 | "帮我想想要不要做 X" | "把这个方案逐题问清楚 / grill me" |

两者都不进行正式实施、都可按授权落盘 explorations 笔记、都能交接主流程；exploring 的受控 spike 仅适用于其自身授权实验，不能扩展为 clarifying 独立会话的实施权限——选错了也能中途换，向用户说明即可。

## Codex 规范

- 普通提问保持一次一题；具体取舍给 2-3 个互斥选项且推荐在首位，目标尚未成形时可开放提问，等待用户明确回复
- 相关披露与问题合在同一条消息，篇幅按实际未知裁剪，不重复已知背景
- 深度推演无 sequential-thinking skill（插件内嵌）可用时降级为回复内分点推演并注明工具降级原因
- 澄清前探索在沙箱禁网时以 `rg` + 文件阅读完成，不依赖 web_search
- 落盘失败（沙箱 read-only）→ 向用户说明并请其自行保存内容
- 独立会话模式轻量，不强制 `update_plan`

## Red Flags

- "推荐很明显，替用户选了吧" → 不得自代；沉默与挂起不是同意，已有明确决定也不重问
- "先凑齐三段披露再问" → 先读上下文，只说明相关未知和风险；格式不等于理解
- "普通澄清也一次多问几个" → 一次一题；设计审查补问只按对应环节的例外执行
- "这个事实问用户最快" → 环境能答的自己查
- "上游还没定，先把下游问了" → 按决策依赖排序
- "澄清完顺手把代码写了" → HARD-GATE，走出口 1
- "共识达成，自动落盘个笔记" → 三出口是提议制，用户没选就不落盘
- "被引用时也走一遍三出口" → 被引用模式的终点是把控制权还给引用方
