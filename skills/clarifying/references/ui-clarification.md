# 通用澄清与界面原型澄清

> 阅读时机：exploring、requirement-analysis、quick-fix 或 visual-preview 需要处理界面相关未知时。沿 clarifying 被引用模式，调用方保留流程控制权，不为每屏开启三出口。

通用 clarifying 先处理目标、角色、范围、业务规则、约束和成功标准。界面 clarifying 处理信息组织、布局、操作路径及状态。两者是同一套提问纪律的适用上下文，不要求机械执行两轮；已有决定和环境可查事实直接复用，不为流程凑问题。

## 提问与反馈循环

1. 读已有规范/原型/裁决，指出当前真正未知；决定来自哪里与 Agent 自行选择的细节分别说明。
2. 在必要信息足够时展示原型。按依赖先解决用户任务与操作流程，再处理布局、交互状态和仍有选择空间的视觉细节。
3. 每轮只问一个实质决策。可在同屏比较相同数据和状态下的方案，推荐项说明原因；不要把业务范围、技术机制和视觉偏好塞进同一个选项。
4. 用户点击/标注/备注后更新当前原型，再核对该问题。局部确认仅关闭该问题，完整设计批准仍需明确来源和版本。
5. 原型暴露业务歧义则回通用澄清，保留其他已决事项；当前范围清楚后回调用方下一阶段。

exploring 保持开放探索，只对影响当前方向的未知收敛；requirement-analysis 覆盖交付范围内的必要决定；quick-fix 的症状不清先问触发与预期，诊断后仅把真实修法/范围取舍交用户，根因事实由证据证明。

原型启用、关闭选择、事件绑定和定稿交接以 [原型契约](../../visual-preview/references/ui-prototype-contract.md) 为准。预览产物可沿上游已有设计授权写入隔离的 visual/spec-assets 位置；不把这项设计活动当作生产实现授权。独立 clarifying 只有用户已要求原型或已授权视觉设计时才创建这些产物，其他独立会话的保存与三出口规则保持。
