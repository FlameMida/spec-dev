# 通用澄清与界面原型澄清

> 阅读时机：exploring、requirement-analysis、quick-fix 或 visual-preview 需要处理界面相关未知时。沿 clarifying 被引用模式，调用方保留流程控制权，不为每屏开启三出口。

通用 clarifying 先处理目标、角色、范围、业务规则、约束和成功标准。界面 clarifying 处理信息组织、布局、操作路径及状态。两者是同一套提问纪律的适用上下文，不要求机械执行两轮；已有决定和环境可查事实直接复用，不为流程凑问题。

## 提问与反馈循环

1. 读已有规范/原型/裁决和 [项目界面约定](../../visual-preview/references/project-ui-conventions.md) 的盘点结论，指出当前真正未知；先知道谁要完成什么、当前要决定什么。未决业务规则只在会影响当前画面或操作结果时阻塞这一题，不等所有问题答完才展示，也不画满尚未确定的功能。
2. 选择能回答这一题的表达：概念和范围留在对话；简短文字草图能讲清流程时就用草图；需要比较实际布局或操作时沿原型入口展示 HTML。先用户任务与操作流程，再布局/状态，最后才是尚有选择空间的视觉细节。
3. 每轮只问一个实质决策。比较方案使用同一任务、数据和状态，展示真正不同的画面或操作，附推荐及取舍；不要只把 A/B 文字搬进卡片，也不要把业务范围、技术机制和视觉偏好塞进同一个选项。
4. 合并文字与绑定到版本的事件，简短复述“采用什么、为何、还有什么未定”；已有明确决定直接消费。只有探索性点击或反馈冲突时，补问当前差异。修改已有明确反馈可直接出新版本，不为每次重绘重问；新增实质取舍才重新澄清，局部确认不替代完整设计批准。
5. 原型暴露业务歧义则回通用澄清，保留其他已决事项；当前范围清楚后把已决行为、理由、适用原型与未决点交回调用方。记录进已有上下文或设计材料，不新建一套决策日志。

项目还没有前端，或缺组件库这类决定界面长相的层时，技术栈选型属于通用澄清：按项目界面约定里的规则先自查，再逐题盘问并给出整套推荐，由用户裁决。裁决之前只用线框回答信息组织和流程问题。

exploring 保持开放探索，只对影响当前方向的未知收敛；requirement-analysis 覆盖交付范围内的必要决定；quick-fix 的症状不清先问触发与预期，诊断后仅把真实修法/范围取舍交用户，根因事实由证据证明。

原型启用、关闭选择、事件绑定及决定落到 spec/plan 的方式以 [原型契约](../../visual-preview/references/ui-prototype-contract.md) 为准。预览产物可沿上游已有设计授权写入隔离的 visual/spec-assets 位置；不把这项设计活动当作生产实现授权。独立 clarifying 只有用户已要求原型或已授权视觉设计时才创建这些产物，其他独立会话的保存与三出口规则保持。
