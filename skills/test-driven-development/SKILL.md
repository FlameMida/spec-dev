# 测试驱动开发（TDD）

新增或改变行为默认先写测试：在公共边界观察到有效失败，再做最小实现并确认通过。

**有效红**指测试已经运行到目标断言并失败，证明这个断言能抓住目标差异。编译或导入错误、缺环境、零测试、SKIP 都不算红，也不算通过。

## 测试写在哪

测试落点是能观察公共行为的边界：模块的公共函数、CLI、HTTP API、页面、数据库适配器。优先用 spec 和计划已经写明的接口与 Scenario；一个落点可以覆盖多个场景，不逐个私有函数造测试。

落点缺失或与契约冲突时停下，走调用方的澄清或偏差流程，不自行改计划、不为测试另开生产接口。

## 红绿循环

1. **写失败测试**。写明输入、动作和可观察结果，期望值来自契约或独立真值；有 Scenario 时测试名沿用 Scenario 名。替身怎么选见 [mock 与测试反模式](references/testing-anti-patterns.md)。
2. **确认有效红**。实际运行，看到目标断言失败。测试直接通过时，先核实它是否真的复现了差异，不人为破坏测试来制造失败。
3. **最小实现**。只实现这个行为，不顺手加功能，不做无关重构。
4. **确认绿**。运行目标测试和项目已有的快检（typecheck、lint）。
5. **提交并记录**。留下测试名、红的原因、绿的提交。

## 运行范围

循环里只运行目标测试和快检。受影响范围、全量回归、E2E、真实模型评测都不在循环里跑，是否运行由用户决定；执行计划时在全部任务完成后的询问门统一问。

本次引入的失败必须修。与当前改动无关的失败用例，只把它在改动前的提交上复跑一次来判定归属并如实记录，不扩大成清理所有历史失败和告警。项目把 warning 视为失败时照项目规则执行。

## 测试锁定

已经提交的测试断言不得为了转绿而修改、删除或跳过。测试本身写错，或契约已经获批变更时，先说明原因并取得确认，再改测试。

## 既有实现的补测恢复

实现已经先于测试存在时，保留它并记录来源，不机械删掉重写，也不覆盖别人的工作。在临时副本或修复前的版本上运行同一个测试，观察到目标行为失败，再对当前实现运行并记录通过；比较时测试和执行条件保持一致，确保前态的失败不是编译或环境错误。没有可恢复的前态就如实记录证明力的缺口，不编造失败。

这样的记录证明测试有回归检测能力，不能证明测试先行。后续的新行为仍按正常红绿执行。

## 纯重构

先核实公共行为不变，用同一组行为测试记录调整前后都通过。缺行为测试时，先依据现行契约补上并确认它在当前实现上通过，再调整结构；这次通过不是红。发现现有行为与需求不符，转为缺陷修复，走正常红绿。

## 外部依赖怎么处理

| 依赖 | 做法 | 能证明什么 |
|---|---|---|
| 外部 API | 在声明的边界注入覆盖实际消费契约的客户端替身 | 替身通过只证明本地消费者 |
| 数据库 | 优先真实测试库；纯内存替身只用于局部确定性行为 | 真实约束与事务要用真实库验证 |
| 时间与随机性 | 注入可控的时钟或随机源 | 不替换被测的业务算法 |
| 文件系统 | 目的允许时用真实临时目录 | 真实 IO 行为 |

依赖注入和窄接口服务于已有的交付需求，不为测试投机新建抽象。替身通过不能当作真实集成的信心。

## 例外清单（单点定义）

一次性原型、生成代码、配置文件，以及不改变行为、契约或测试预期的纯文案，可以按可追溯的授权跳过先行测试；同范围已有授权就引用原决定。技能规则、API 语义和测试预期即使写在 Markdown 里也不是纯文案。补测恢复要如实记录偏差，不能成为以后先写实现的默认许可。

## 完成依据

记录实际走的是哪条路：先行红绿、纯重构前后绿、补测比较，还是获批例外。写明对应的公共入口与 Scenario、失败时的输出、未验证的范围和授权来源。不同路径的证据不能互相冒充。
