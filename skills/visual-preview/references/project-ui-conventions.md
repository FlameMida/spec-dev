# 项目界面约定与原型保真

> 阅读时机：画第一版界面原型之前；整理定稿时；向 spec 和计划交接组件映射时。图示、架构图这类非界面内容不需要本文件。

项目界面约定指本项目已经定下来、新页面应当沿用的东西：技术栈、组件库与版本、设计令牌、公共封装组件、布局壳和参照页面。原型按它绘制，实现才能照着原型还原。

## 盘点

盘点靠读项目，不问用户。先读项目规范文件，再读前端代码，逐项记下结论和证据路径：

| 项 | 要确认的内容 | 证据 |
|---|---|---|
| 技术栈 | 框架与语言、构建器、路由、数据请求与状态管理 | 依赖清单、构建配置 |
| 组件库 | 名称、锁定的版本、图标集 | 依赖清单与锁文件 |
| 设计令牌与样式 | 样式方案（静态样式表、预处理器、原子类、运行时样式）、主题文件，颜色、间距、字号、圆角的令牌，是否支持深色 | 主题与全局样式文件、样式配置 |
| 公共封装组件 | 项目自己封装、供各页面复用的组件（页面容器、表格、表单、搜索栏、弹窗等）：路径、用途、关键属性 | 组件目录，以及实际使用它的页面 |
| 布局壳 | 导航、页头、面包屑、内容区的宽度与间距，页面标题和操作区放在哪里 | 布局组件、路由配置 |
| 参照页面 | 与本次需求最接近的一到两个现有页面：信息密度，列表、表单、详情的惯用排法，加载、空数据、错误的惯用表现 | 页面源码；应用能运行时实际打开看 |

- 仓库里有多个前端工程时，先确定本次需求落在哪一个。
- 找不到的项写"未找到"，不猜，也不拿通用做法顶替。
- 把结论整理成几行**约定摘要**，随第一屏告诉用户原型是按什么画的，之后写进 spec 的关键决策。
- 同一项目后续的原型复用已有摘要，只核对有没有变化。

## 没有前端时：先定技术栈

盘点发现项目还没有前端、而本次需求需要界面时，先把技术栈定下来再画定稿。项目有前端但缺组件库、样式方案这类决定界面长相的层时，只补缺的那一层。用户已经指定的部分直接采用，不重问。

1. **先自查**。项目规范文件和 ADR 里的既有约定；同仓库或同组织其他前端的选型；后端的技术栈与接口形态（有没有能生成类型的接口契约）；部署和运行约束（静态托管、内嵌进后端、内网不能访问外网）；已有的设计稿或品牌规范。
2. **再盘问**。按 clarifying 的纪律一次一题，推荐放首位，只问会改变选型的：
   - 产品形态与设备：管理后台、门户或内容站、移动端网页、小程序、桌面端。
   - 首屏与搜索引擎：要不要服务端渲染或静态生成。
   - 团队熟悉什么，有没有必须遵守的公司规范。
   - 界面复杂度：复杂表格、表单、图表占多大比重。
   - 主题、深色模式、国际化。
   - 浏览器与设备的兼容范围。
   - 与后端同仓库还是独立仓库。
3. **给整套推荐**。一次给出框架与语言、构建器、组件库、样式与令牌方案、路由、数据请求与状态、表单与表格、国际化、测试与静态检查、目录组织，以及首批要封装的公共组件和布局壳。每项一句理由；备选各用一句话说明为什么不选。版本号、维护状态和各项之间的兼容性是外部事实，按外部搜索入口核实并注明来源与日期，不凭记忆报版本。
4. **用户裁决后落点**。requirement-analysis 里把选型写进 spec 的关键决策，满足 ADR 三条件的另存 ADR；exploring 里只当作本次探索的假设记录，不算项目决定。
5. **批准设计前不搭生产脚手架**。原型要用的组件库资源放在隔离的 `visual/` 目录里；脚手架、布局壳和令牌由计划的第一个任务落地。

用户裁决之前，可以先用线框回答信息组织和流程问题，不拿某一套组件库的观感暗示选型。

## 草稿与定稿

- **草稿**回答当前这一个问题。信息组织和流程用线框或局部原型就够，保真度见 [preview-guide.md「设计要点」](preview-guide.md#设计要点)。
- **定稿**是实现要照着还原的版本，必须按项目界面约定绘制，线框不当定稿。

定稿的渲染方式按下表从上到下取第一个可行的：

| 档 | 做法 | 前提 |
|---|---|---|
| 真实组件 | 在特性目录的 `visual/` 下建隔离入口，直接引用项目的公共封装组件和布局壳，配上模拟数据，用项目自己的构建器打成静态文件放进 `screen_dir` | 依赖已安装，项目构建器能对隔离入口出包；项目已有组件演示环境时优先复用 |
| 同库静态 | 把同版本组件库的静态样式和项目的主题、全局样式复制进 `screen_dir`，按真实组件渲染出来的结构和类名手写 HTML | 组件库有可直接加载的静态分发文件 |
| 等价演示 | 用设计令牌和近似结构演示 | 前两档都不可行 |

- **不改生产文件**。隔离入口、构建配置和产物都在 `visual/` 目录内，不改项目的生产源码、路由、配置和依赖。需要新增依赖时，那是设计决定，回澄清。
- **降档要说明原因**。同库静态和等价演示不是真实组件，逐条列出**已知偏差**：哪些交互是仿制的，哪些样式要等实际页面核对。
- **定稿屏写完整 HTML 文档**。frame 的全局样式会改变组件库的默认表现；完整文档不经 frame 包裹，用户的意见在对话里收。写法见 [preview-guide.md「定稿屏与项目资源」](preview-guide.md#定稿屏与项目资源)。
- **资源全部本地化**。远程资源无法归档。真实组件档打成单个经典脚本和单个样式文件，不做代码分割，归档才不会漏掉分块。
- **窄屏用真实宽度核对**。frame 的视口切换只收窄容器，不触发媒体查询。
- **数据像真的**。用项目代表性的内容，包含会撑开布局的长名称、多行数据和各状态。

## 组件映射表

定稿必须附组件映射表。它说明原型的每个区域在实现时用项目的哪个组件，是计划切任务和实施还原的依据。

| 原型区域 | 项目组件与变体 | 源码路径 | 类型 | 说明 |
|---|---|---|---|---|
| 订单列表的筛选栏 | `SearchForm`，三列行内 | `src/components/SearchForm` | 复用 | — |
| 订单表格 | `DataTable`，带行选择 | `src/components/DataTable` | 扩展 | 需要加批量操作插槽 |
| 批量操作条 | — | — | 新增 | 现有组件没有吸底操作条 |

- 类型只有三种：**复用**、**扩展**、**新增**。扩展写清要加的属性或变体；新增写清现有组件为什么不够。
- 粒度到页面骨架和主要区块，不到每个按钮。直接使用的组件库原生组件不必逐个列出，只列项目封装层和布局壳。
- 表后附**还原要点**：布局（栅格、间距、对齐）、文案、各状态的表现，以及用到的令牌里容易走样的地方。
- 项目还没有前端时，"项目组件"一栏写选定组件库的组件和计划首批封装的组件，类型都是新增。
- 映射表和还原要点写进 spec 的关键决策；行数多时另存为 `spec/assets/<定稿名称>-mapping.md`，spec 里留一行指针。

## 定稿自检

请用户审查定稿之前，代理先自己过一遍：

- 约定摘要的每一项都有证据路径；映射表覆盖了定稿里的全部区域；已知偏差已经列出。
- 在浏览器里实际打开每一屏：没有控制台错误，资源都从本地加载，各状态走得到；项目支持深色时两种主题都看；适用的窄屏用真实宽度看。
- 没有浏览器能力时，明确说出哪些没有自检，不写成已验证。
