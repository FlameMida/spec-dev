# 界面原型与交接契约

> 阅读时机：判断界面预览入口、确认原型、向 spec/plan/验收交接时。本文件定义触发与产物；提问纪律归 clarifying，复验归 test-strategy，验收结论归 acceptance-qa。

## 自动触发与例外

新增页面、重新设计、主要布局/导航/信息层级/核心交互变化，在通用澄清已提供足够信息时自动展示第一版 HTML，不单独询问是否启用。不按代码行数判断影响。局部文案/间距等预期明确的小改动可以跳过原型设计，但修后仍须实际查看/操作受影响状态并回放原症状；内部重构且用户可见行为不变不适用；用户明确关闭预览时消费该决定，直到用户改变选择。已有适用定稿直接复用，仅展示受影响差量。

exploring 先澄清探索目标，在实际决定比较界面方案时使用本规则；仅谈论 UI 或尚不清楚要探索什么时不启动空原型。quick-fix 仅恢复既定行为时直接回放实际页面，出现重新设计按其既有升级与授权规则转交。工具不可用时声明未完成和具体条件，不能把未启动记成用户关闭，也不能静默假定预览批准；替代展示沿用户已认可的方式。

## 通用澄清与原型澄清

先读取现行规范、公共组件和已有决定，按 [界面澄清](../../clarifying/references/ui-clarification.md) 处理未知。以项目组件/设计令牌为优先；不能直接复用时声明等价演示及尚需实际页面核对的差异。原型是可交互 HTML，数据可以模拟，模拟保存/授权/价格等边界须说明。

按实际需求展示角色/入口、正常/空数据/加载/错误/无权限、编辑/保存中/保存失败及适用窄屏。只选能改变交付判断的状态，不机械生成排列组合。场景名称与 spec Scenario 对应；原型发现业务歧义时返回通用澄清，已有决定不重问。

## 确认与版本

- 每屏及其关联 CSS/JS/图片使用固定版本，变更资源时生成新的原型版本；render_sha256 绑定渲染 HTML，资源字节由归档 manifest 另核，不能据该哈希宣称动态资源也已验证。每屏使用唯一文件名。`click`、`choice`、`annotate`、备注只表示反馈；`confirm` 也仅确认屏上明确提出的当前问题，不能自动批准整份设计。
- 事件的 `screen_file`、`screen_sha256`、`render_sha256` 与 `binding_verified` 识别实际展示版本。旧页、排队重发或缺绑定的确认不能归到最新页；核对本次问题及备注。`binding_verified` 只证明事件引用曾渲染版本，不证明用户批准了实现或全设计。
- 用户明确确认完整设计时，把适用页面和状态、该版本及确认来源并入既有设计批准。文字确认同样有效，须指向明确版本；沉默和推荐选项不算同意。
- 实质设计变化只重开受影响决定，更新原型和 spec；原型、spec 或用户决定冲突时先澄清该差异，不由执行者任选一个。

## 定稿与后续消费

沿 visual-preview 的归档命令保存明确历史屏到 `spec/assets/<名称>/index.html`，连同资源和 manifest 入库。manifest 保存来源屏幕与内容哈希、产物哈希；它不是批准记录。只含内联样式/脚本的独立 HTML 可继续使用 `spec/assets/<名称>.html`，须证明必要资源可用。关闭原服务后重新打开归档，实际查看关键交互；远端资源、动态 import/fetch、路由或模块加载限制必须补齐或明确未验证，不能凭导出成功宣称离线可用。

在现有 spec「已确认的关键决策/测试与验收策略」中记录，不新建进度源：

| 原型路径与版本 | 适用角色/视口/状态 | 已确认交互 | 模拟业务边界 | 确认来源 |
|---|---|---|---|---|
| 相对 spec 的 HTML 路径及 manifest/文件 SHA-256 | 本次实际范围 | 与 Scenario 对应 | 哪些结果由演示产生 | 明确确认的对话或绑定事件 |

writing-plans 继承此版本与场景，把第一条真实用户闭环安排到最早可运行切片。executing-plans 在该切片就绪时实际操作并对照原型。acceptance-qa 以相同角色、数据、操作和视口对照实际页面，核验真实业务证据；首次截图建线不能替代定稿对照。用户关闭预览时使用已确认的文字/既有界面契约，保留必要业务验证。
