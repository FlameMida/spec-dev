# 可视化预览（Visual Preview）

在浏览器里给用户看原型、图示和可点选的方案，用户的选择会回到对话。只有看图比读文字更清楚的问题才用它。

## 自动入口与共享契约

第一次判断要不要出原型，或要交接定稿时，先读 [界面原型与交接契约](references/ui-prototype-contract.md)。

新增页面、重新设计，或主要布局、导航、信息层级、核心交互有变化时：需求基本清楚后直接出第一版，不用先问要不要开预览。局部小改动可以不出原型，但改完要实际打开页面看一遍。用户说过不要预览就不再启动，也不再问。已有可用的定稿直接用。

在 exploring 里，先弄清要探索什么，确实需要比较界面时再出原型；纯概念问题留在对话里。提问按 [界面澄清](../clarifying/references/ui-clarification.md)：围绕眼前这一个问题尽早给出最小的草稿，不等整份需求定下来；一次解决一个决定，问完回到调用它的 skill。出了原型不等于设计已获批准。

## 先盘点项目界面约定

画第一版界面原型前，按 [项目界面约定](references/project-ui-conventions.md) 盘点技术栈、组件库与版本、设计令牌、公共封装组件、布局壳和参照页面。事实靠读项目取得并留证据路径，不问用户；结论整理成约定摘要，随第一屏告诉用户。

- 项目还没有前端，或缺组件库这类决定界面长相的层：先按同一文件的规则盘问并推荐技术栈，用户裁决后再画定稿。
- 草稿回答当前这一个问题，可以用线框。定稿是实现要照着还原的版本，按约定绘制并附组件映射表，线框不当定稿。
- 图示、架构图这类非界面内容不需要盘点。

## 逐题判断：浏览器还是终端

预览启用后，仍要**对每个问题单独判断**。判据：**用户看到它会比读到它理解得更好吗？**

- **用浏览器**：内容本身是视觉的——mockup、线框图、布局对比、架构图、并排视觉方案、观感/间距/视觉层级问题
- **用终端**：内容是文字的——需求问题、概念选择、取舍清单、A/B/C 文字选项、范围决策

涉及 UI 的话题 ≠ 视觉问题。"这个向导的『个性化』指什么？"是概念问题——用终端；"哪种向导布局更好？"是视觉问题——用浏览器。

## 启动会话

**主动展示**：原型要打开在用户面前，不只发链接。宿主有页面预览能力时用它打开；否则在本机交互环境启动时带 `--open`，第一屏就绪时服务会在用户的系统浏览器里打开预览，之后的新屏在同一标签页自动刷新。远程、无头或打不开时给出完整 URL，并明说没有自动打开。用户已经关闭预览时不启动、不打开。无论是否自动打开，每一屏都重发完整 URL，并说明这一屏要看什么。

代理查看、操作和验证原型时，先读取官方 `ego-browser` skill，执行 `ego-browser skill` 并完整读取当前版本指南，通过 ego-lite 打开下方服务器返回的 URL；同一目标复用一个 TaskSpace。接入与缺失处理见 [浏览器接入](../acceptance-qa/references/browser-setup.md)。用户打开预览链接不等于代理已完成页面验证；缺少浏览器能力时明确说明未验证。

```bash
# 命中自动入口或已有明确预览请求后启动；将返回 URL 交给 ego-lite。--project-dir 支持持久化和同端口重启。
# --open：第一屏就绪时在用户的系统浏览器里自动打开预览；远程、无头环境不带。
# --theme-css <file>：注入项目的 design tokens/CSS 变量，让 frame 里的草稿用项目自己的配色；盘点到令牌文件时带上。
# ${CLAUDE_SKILL_DIR} 由平台替换为本 skill 目录；未替换时取 skill base directory。
bash "${CLAUDE_SKILL_DIR}/scripts/start-server.sh" --project-dir /path/to/project --open
```

| 情况 | 启动参数 | 原型文件位置 |
|---|---|---|
| 正在做某个特性的设计或计划 | 必须加 `--feature-dir .spec-dev/<当日特性目录>` | `<feature-dir>/visual/<session-id>/` |
| 其他 | 不加 | `<project>/.spec-dev/visual/` |

端口和密钥的记忆文件始终放在 `.spec-dev/visual/`，各特性共用端口。启动返回的 JSON 含 `port`、`url`、`screen_dir`、`state_dir`，记下后两个。两个 visual 目录里的 `.gitignore`（内容 `*`）由脚本自建，不用改仓库的 `.gitignore`。**不要忽略整个 `.spec-dev/`**：spec、计划和 roadmap 需要提交入库，漂移守卫也依赖已提交的 spec。

**URL 里带会话密钥（`?key=…`）**：给用户的必须是 `url` 字段的完整 URL，连同 query string；HTTP 和 WebSocket 访问都要靠这个密钥。

**平台差异**：

| 平台 | 启动方式 |
|------|----------|
| Claude Code | 直接运行，脚本自行后台化；Windows 下自动转前台，需在 Bash 调用加 `run_in_background: true`，下一轮读 `$STATE_DIR/server-info` 取 URL |
| Codex | 脚本检测 `CODEX_CI` 自动转前台，正常运行即可、无需额外参数 |
| 其他 | 若环境回收后台进程，用 `--foreground` + 平台自身的后台执行机制 |

远程/容器环境浏览器连不上时：`--host 0.0.0.0 --url-host localhost`（此时启动 JSON 的 `lan_urls` 列出局域网地址，可给用户在手机上打开，看移动端 mockup 更真实）。

## 循环

1. **写新一屏**：
   - 先确认服务器还在：`$STATE_DIR/server-info` 存在且 `server-stopped` 不存在。已经停了就用相同的 `--project-dir` 重启，端口沿用，已打开的标签页会自动重连。
   - 把 HTML fragment 写进 `screen_dir` 的新文件，服务器会自动展示最新的文件。文件名表达内容（如 `layout.html`），不重复使用旧文件名。
   - 浅色和深色主题下的配色都要检查。
   - 用文件创建工具写，不用 cat 或 heredoc。
   - 定稿屏写完整的 HTML 文档。
2. **展示当前问题并等待反馈**：确认页面已经打开在用户面前，重发 URL（每一步都发），简述画面和要决定的一件事；有真实选项时给推荐与取舍，请用户在对话回复或使用屏上反馈。当前问题用户已经明确回答了就直接采用，不另问“这一屏是否通过”
3. **下一回合**：读 `$STATE_DIR/events`（JSON lines，浏览器交互记录）——终端文字是主反馈，events 提供结构化补充；`type:"confirm"` 仅确认当前屏上的问题（含随附备注），核对 `screen_file/screen_sha256/render_sha256/binding_verified`，`click` 带 `selected` 区分选中/取消，`annotate` 是用户点选的"要改的位置"；文件不存在说明用户没和浏览器交互
4. **复述并迭代**：按界面澄清的做法，归纳已采纳的决定、理由和还没定的点；要改当前屏就写新文件（`layout-v2.html`）。当前问题定了就往下走。没被选中的草稿和模拟出来的结果不算需求；交接方式见下面的归档约定
5. **回到终端时卸载**：下一步不需要浏览器时推一张等待屏（`waiting.html`：「继续在终端讨论…」），避免用户盯着已解决的选择题
6. 重复直至完成

fragment 写法、可用 CSS 类、events 格式、命名细则见 [preview-guide.md](references/preview-guide.md)。

**主题适配**：fragment 的文字与背景使用主题变量，不锁定全局浅色或深色；接入组件库时检查内容区和弹层是否跟随 frame 切换，具体规则见 [preview-guide.md「设计要点」](references/preview-guide.md#设计要点)。

## 定稿审查

界面决定都已落定、调用方准备请求批准设计之前，让用户把定稿通看一遍。它并入既有的设计批准，不单设批准门。

1. **整理定稿**。按 [项目界面约定](references/project-ui-conventions.md) 把采纳的各屏做成定稿，附组件映射表、还原要点和已知偏差。
2. **推定稿总览屏**。列出每个页面、状态和视口的入口（`/screen/<文件名>`），以及约定摘要、组件映射表、模拟边界和已知偏差。
3. **先自检**。按约定文件的「定稿自检」在浏览器里逐屏过一遍；缺浏览器能力时说明哪些没有自检。
4. **请用户通看**。确认总览屏已经打开在用户面前，告诉用户按什么顺序看、每屏要判断什么。
5. **收束**。修改意见出新版本，只重看受影响的屏。用户认可后按下方归档约定固定版本，把版本交给调用方写进设计提案。

定稿还没有展示给用户看过，调用方就不请求批准界面；用户明确关闭预览时改用已确认的文字。

## 清理

```bash
bash "${CLAUDE_SKILL_DIR}/scripts/stop-server.sh" "$SESSION_DIR"
```

项目内会话同规则：特性目录下的 `visual/` 会话与 `.spec-dev/visual/` 会话的 mockup 均保留供日后查看（`stop-server.sh` 的删除逻辑只认 `/tmp` 前缀，特性目录会话自然保留）；仅 `/tmp` 会话在停止时删除。

**归档约定**：被设计采纳的定稿及必要资源保存到 `spec/assets/` 入库；会话状态与密钥不入库。对明确历史屏使用：

```bash
node "${CLAUDE_SKILL_DIR}/scripts/archive-preview.mjs" --url "<含 key 的 /screen/定稿文件.html URL>" --out "<特性目录>/spec/assets/<定稿名称>"
```

产物为 `index.html`、`assets/` 和 `manifest.json`，已有目标拒绝覆盖。导出器保留静态资源与来源版本、禁用离线反馈传输，不产生批准记录；外部资源或 srcset 需先本地化/打包。动态 import/fetch 和路由仍须实际打开归档验证。关闭原服务后检查关键交互，将确认来源与适用状态写入现有 spec，交接细则见 [界面原型与交接契约](references/ui-prototype-contract.md)。仅有内联资源的独立 HTML 可保留单文件形态。
