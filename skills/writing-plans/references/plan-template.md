# 计划模板

> 阅读时机：写任何新计划之前。

## 整体结构

一份计划就是一个 Markdown 文件，依次是头部、任务导航、各任务、执行记录。

````markdown
# [功能名] 实施计划

> **执行方式**：用 executing-plans skill 逐任务执行；没有该 skill 的环境从任务 1 起按序执行。进度只看本文件的复选框，完成一步勾一步。
>
> **偏差处理**：小偏差（路径笔误、意图明确的遗漏）就地修正并记入执行记录；接口、数据结构等契约级偏差停下问计划作者，不猜着改。

**目标**：[一句话说明构建什么]

**Spec**：[spec 路径；没有 spec 时写"无"，并在下面列验收标准]

**非目标与全局约束**：[不做什么；版本、依赖、命名、平台等硬约束，数值从 spec 逐字复制]

**架构与关键取舍**：[2 到 3 句方案概述；只列影响任务边界或顺序的取舍，指向 spec 小节]

**测试命令**：

- 单个测试：[如 `pytest tests/test_pagination.py::test_name -v`]
- 快检：[项目已有的 typecheck 或 lint 命令；没有写"无"]
- 受影响范围：[项目已有的影响分析命令；没有则写"本计划新增或修改的测试文件，加上直接引用被改源文件的测试"]
- 全量：[完整测试套件命令]

**收尾预先决定**：做完再问
````

## 头部

头部是开工和恢复时都要读的公共内容，只放跨任务必需的信息：

- **目标、非目标与全局约束**是执行期判断跑偏的参照，每个任务开工都会重读，写具体。
- **架构与关键取舍**只做摘要并指向 spec，不复制决策论证；某个任务专属的细节留在任务节。
- **受影响范围**的推导顺序：项目已有影响分析工具就写具体命令（如 `nx affected -t test`、`jest --changedSince`、`pytest --testmon`），以项目的依赖和配置清单为准；没有工具就按模板里的文字规则，只向外推一层，不按目录把无关测试圈进来。
- **收尾预先决定**只有两种写法：默认的"做完再问"，或用户的明确选择（如"回归：受影响范围；验收：不做；交付：PR"）。不替用户填。

## 任务导航

- 任务 ID `TNN` 对应同文件的 `### 任务 N`，编号全局唯一、从 1 开始。
- 依赖只写真实前置：后一个任务确实要用前一个任务落地的代码、接口或数据。编号相邻不等于有依赖，不为了排顺序加假依赖；不能有环。
- 接口写精确签名。产出接口是给依赖方读的，不是逐函数的测试清单。

## 任务节

- 每个任务五步，复选框格式固定为 `- [ ] **步骤 N：…**`。
- **有效红**指测试已经运行到目标断言并失败。编译或导入错误、缺环境、零测试、SKIP 都不算，它们只说明测试还不能验证这个行为。步骤 2 的预期要写出失败的具体表现。
- 步骤 4 只运行本任务的目标测试和快检，不写受影响范围或全量命令。
- 一个任务覆盖多个 Scenario 时，步骤 1 和步骤 2 逐个列出测试。
- **纯重构任务**把五步换成：确认现有行为测试通过、调整结构、再次通过并跑快检、提交。缺行为测试时第一步先补，并确认它在当前实现上通过。
- 「红转绿记录」留给执行者填写，每个 Scenario 测试一行。

## 执行记录

计划生成时留空。执行者在这里写工作区与分支、对计划的就地修正、任务外发现、Requirement 对账和实际交付方式。它和复选框一起构成恢复所需的全部状态，不另建进度文件。
