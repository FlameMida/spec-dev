# 设计原则（方案取舍与计划编写共同遵循）

> **阅读时机**：requirement-analysis 写设计提案、writing-plans 切任务时读取；审查按需引用其中的模块判据。

八条原则（方案评价维度与任务分解检查项）：

1. **默认不保留向后兼容性**。删除过时路径，而不是添加兼容层、回退垫片或仅用于兼容性的数据迁移。常规的前向模式迁移仍然是必需的。只保留产品和部署规则里明确写着的现行契约。
2. **选择能完全满足当前需求的最简单实现**。避免推测性的抽象、配置和间接层。
3. **分层构建系统**。从能够端到端工作的最小版本开始，然后基于运行中的产品逐步添加各项能力。
4. **宁可交付能用的简单版本，也不留做了一半的复杂方案**。
5. **保持组件模块化，关注点清晰分离**。
6. **优先使用成熟且维护良好的库**，前提是它们能降低整体复杂性或提高可靠性；没有充分理由不重新实现通用功能。
7. **优先使用项目中已有的依赖**；判断某依赖缺少某能力之前，先查阅其文档和类型定义。
8. **做出长期性的架构决策**。不接受打算日后替换的权宜之计。

## 在 spec-dev 里怎么理解

- 第 1 条说的是实现：不写兼容层、垫片和只为兼容而做的迁移。active spec 就是“明确写着的现行契约”，旧 active spec 默认仍然必须遵守；要删掉它规定的行为，先用新 spec 明确取代它，不能绕开。读旧格式的计划这类历史文件属于读历史数据，不算兼容垫片。
- 第 6、7 条：收尾审查会检查是否优先用了项目已有的工具和模式。
- 第 8 条：满足 ADR 三条件的长期决策另存为 ADR。

## 模块判据

设计、写计划、审 spec 和审代码时，用下面四个问题判断一个模块或抽象是否合理。答案只是线索，不直接等于缺陷，也不要求立刻重构。

- **去掉它会怎样**：设想把这个模块拿掉。复杂度随之消失，说明它可能是多余的一层；复杂度散到各个调用方，说明它有用。只做设想，不真的删。
- **有几种真实实现**：列出实际存在的实现和用途。只有一个实现不说明抽象错了，两个也不说明它对；不为凑数造假实现或第二个实现。
- **接口能不能更小**：能否减少方法、简化参数、把更多细节藏在内部？结合实际调用方和现有需求回答。
- **有没有结构上的别扭**：理解一个概念要跨很多模块；接口和内部一样复杂；测试只测了抽出来的纯函数、没测公共调用；内部细节漏给调用方；公共接口难测。只看这次改动新增或加重的。

设计和计划阶段可以据此改方案。审查阶段只报告有实际影响的问题；只是“可以更优雅”的想法记为重构候选，真要重构按 test-driven-development 的“纯重构”一节。

## 迁移与约束

- 分批迁移（先加新的、分批切换、最后删旧的）期间，新旧并存是获准的过渡状态。计划里要写明删除旧形式的任务和最终验证，不让它变成长期兼容层。旧 active spec 规定的行为要变时仍走取代流程。做不到每批都通过测试时，合成一个任务做完并验证，不交付半成品。
- 多个互相独立的约束，定方案时各自写明由哪个模块负责、在哪里验证；一项验证通过不代表另一项也通过。约束写在计划头部，各任务直接沿用。
- 一句话确实能读出两种意思、用户已经定了取哪种时，记下采用的理解、没采用的理解和理由。
