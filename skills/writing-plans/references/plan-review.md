# Self-Review

> 阅读时机：计划草稿完成后、交接之前。

## Self-Review

写完整份计划后，主线程先以新鲜眼光对照 spec 检查下面清单；复杂任务图另做下述只读独立审查。

修订未执行的获批任务时保留其需求、接口、写集与验收意图，同时补全可执行步骤；不能以“保留原任务”为由照抄不完整提纲。已经执行的历史状态、SHA 与证据保持原件，不回填成新稿执行结果。

1. **Spec 覆盖**：逐条 Requirement 过——能指到实现它的任务吗？每个 Scenario 都有适用的行为红绿、纯重构保护或组验证步骤吗（GIVEN/WHEN/THEN → arrange/act/assert）？验收矩阵的「验收任务」行都进入验收任务表了吗？差量三节的 MODIFIED/REMOVED 有对应的改造/清理任务吗？列出缺口
2. **可执行性**：文件/符号、公共接口、前置输入、动作、预期断言和运行命令是否明确？按“禁止占位符”补真正缺口；不因缺少完整测试或实现代码要求补写。
3. **类型一致性**：后续任务用到的类型、方法签名、属性名与前序任务定义一致吗？任务 3 叫 `clearLayers()`、任务 7 叫 `clearFullLayers()` 就是 bug
4. **导航表与任务文件一致**：导航表接口列与各任务文件的接口块逐条一致吗？tasks/ 文件名与表内任务 ID 一一对应吗（plan-index 校验过再交付）？

5. **早期反馈与复验**：能指出第一条真实闭环、适用定稿版本/状态及首次实际运行位置；矩阵 required 与 D/A/X 未被重解释；helper 等局部修复没有无理由全量重跑；必需 manual-pending 未被当成通过。

6. **依赖最小性**：每条边能否指出实际消费接口、验证或安全顺序理由？补漏边、删无理由的边；保留 T00/迁移/验收/最终任务及组出口的必要约束。不能靠删安全边制造并发或消除环；若必要依赖构成环，报告结构不成立并重划任务边界。成员实际消费前序成员接口时也要显式写依赖，members 顺序不代替接口边。同时检查可并发任务是否漏了声明、声明的文件和资源是否与任务一致、不能并发的原因是否写清楚。

有并发潜力时按 [并发准备](parallel-readiness.md) 做一次纸上走查：只给执行者 spec/index/本票/依赖接口，能否无猜测地实现和验证？让一条链先完成，观察后继是否被无关慢票挡住；再让两票碰到公共注册文件或同一测试库，检查冲突是否被精确写集/资源覆盖。逐票独立绿与汇总后的真实组合验证均须有归属；plan-index 的结构通过不能证明这些语义成立。

**任务图语义审查**：存在跨模块不变量、多个切片共享写入或单票验证依赖兄弟票时，自检后、交接前交一个独立只读审查者核对任务边界、真实阻塞边和共享文件所有者。提供 spec、完整计划及必要源码指针，要求给出问题依据或无问题的覆盖说明，不传预设结论，不修改计划、不执行任务、不建 worktree。核对纵向行为是否完整、已批准替换边界是否能独立验证、汇总票职责是否与普通票 writes 矛盾，以及扣除冲突后的实际并发窗口。主线程处置发现后重走受影响图；简单且无这些风险的计划沿自检即可。平台不支持或当前禁止委派时，由主线程单独做第二遍语义审查并注明未独立验证，不为此绕过限制或虚称独立通过。

逐票从声明的仓库根 cwd 手工追踪路径和状态提交：文件在 `<特性目录>/plan/progress.yaml` 时，Git 命令必须包含完整仓库根相对路径；进入子目录后显式返回，不能假定工具会重置 cwd。任务状态、绑定及清理检查点写入后给出独立 Git 提交步骤；例行资源登记和候选日志索引沿 executing-plans 的资源登记节并入必要检查点。完成 SHA 指向已存在的实现/验证提交，不能指向尚未产生且会包含该字段的提交。T00 复用隔离仍执行绑定、基线与完成状态保存，最后的合并/清理仅消费实际登记的所有权。

同时按 [工作区工具边界](../../using-git-worktrees/references/tool-boundaries.md) 审查实际运行能力：创建、会话 cwd 与文件工具边界分别有依据；Git 管理和宿主原生恢复方式不混用；查询结果经独立回执消费后再形成明确命令；需要原子执行的段落有已获准且兼容的稳定入口。不要把可选 RTK 包装、一次 cd 或普通终端成功当作所有宿主都能执行的证明。

路径映射要实际解析：以链接所在文档目录为起点，核对 Spec/Requirement 指针是否落到真实源文件。例如 `.spec-dev/demo/plan/index.md` 中 `../../spec-expand.md` 指向 `.spec-dev/spec-expand.md`，不是仓库根。尚未生成的目录用预期绝对位置在内存解析，再验证映射到的现存源文件；若计划要求复制/建立独立夹具仓库，应给出实际物化步骤和此后的根目录，不能声称嵌套目录已是 Git 根。不要通过执行生成任务验证计划。

内部改名或 expand–contract 保持公开行为时，使用改动前后均通过的公开行为保护；新导出缺失引发的 ESM 链接错误不是有效行为红。若确有新行为，先让测试可执行并观察对应业务断言失败。

对计划中的检查命令同时核对“该步执行前/后的真实文件内容”：未迁移的本票消费者仍可能触发声明的暂时导入失败，不能提前要求它已改好。contract 分两阶段：删除旧定义前，先验证已迁移消费者不再绑定旧符号（此时旧定义/获批过渡别名仍可存在）；删除旧定义并改写新实现对它的依赖后，再检查旧绑定、旧定义均为零并跑公开行为保护。

简单单行具名 ESM 的示例（以下是 **JavaScript RegExp**，不是 grep ERE）：`/\b(?:import|export)\s*\{[^}]*\btrim\b/` 识别旧具名绑定，删除定义后的检查另加 `/\bexport\s+(?:const|function)\s+trim\b/`。`export const trim = s => s.trim()` 必须判为残留；`export const normalize = s => s.trim()` 不能误判。不能宽泛匹配整行 export + trim，也不能用排除含 `.trim()` 的整行过滤掩盖旧导出。其他语法用项目已有解析工具或按真实语法设计检查，不为此新增依赖。测试证据同时保存 stdout/stderr；如 Node TAP 的失败断言在 stdout，不能把 stderr 非空作为行为红的必要条件。逐段检查 shell 引号、括号与目录切换，合并/清理必须消费 T00 记录的实际路径和资源所有权。

组计划逐票走查成功和失败两条路径：检查命令非零之后必须能保存对应 blocked 检查点、定位承担修复的成员与受影响依赖闭包，再恢复和重新验证；仅 `raise` 留锁不等于已完成失败状态保存。按 integration-groups 的调用顺序内嵌入口/检查点预检、会话 owner、证据登记及恢复步骤。静态语法检查在内存完成，不能借自检执行生成任务或创建未登记临时文件。

发现问题就地修复，无需复审；发现 spec 需求没有对应任务就补任务。

新协议另查：scopes 是 writes 唯一来源，plan-index 明示支持 scope_protocol_version:1；F 依赖所有实施/组出口，A 依赖 F，D 依赖 F/A，F 不反向等待验收。逐票核对 scope_commit→状态 authority→本地 bind 的真实提交顺序；已有记录只补当前/未执行项。D 要给出原件转存、存活目标、history_ref、实际合并回执、verifyDelivery 及失败保全步骤；修复后回到补验、受影响复审和验收对账，不能直接合并。
