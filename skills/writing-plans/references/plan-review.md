# Self-Review

> 阅读时机：计划草稿完成后、交接之前。

## Self-Review

写完整份计划后，主线程先以新鲜眼光对照 spec 检查下面清单；复杂任务图另做下述只读独立审查。

修订未执行的获批任务时保留其需求、接口、写集与验收意图，同时补全可执行步骤；不能以“保留原任务”为由照抄不完整提纲。已经执行的历史状态、SHA 与证据保持原件，不回填成新稿执行结果。

1. **Spec 覆盖**：逐条 Requirement 过——能指到实现它的任务吗？每个 Scenario 都有适用的行为红绿、纯重构保护或组验证步骤吗（GIVEN/WHEN/THEN → arrange/act/assert）？验收矩阵的「验收任务」行都进入验收任务表了吗？差量三节的 MODIFIED/REMOVED 有对应的改造/清理任务吗？按 [审查关注点](plan-format.md#计划文档头部) 核对已有来源的具体失败条件能否落到负责的任务和断言，避免只写“注意风险”。列出缺口。
2. **可执行性**：文件/符号、公共接口、前置输入、动作、预期断言和运行命令是否明确？适用的调用示例与任务接口、失败断言是否一致？按“禁止占位符”补真正缺口；不因缺少完整测试或实现代码要求补写。
3. **类型一致性**：后续任务用到的类型、方法签名、属性名与前序任务定义一致吗？逐个核对实际消费与产出签名。
4. **导航表与任务正文一致**：导航接口与同文件任务节逐条一致吗？TNN 与 `### 任务 N` 一一对应吗，复选框是否完整？

5. **早期反馈与复验**：采纳的界面决定能否指向对应任务的入口、动作、可观察断言和验证方式，原型中的模拟结果由哪票接成真实行为？能指出第一条真实闭环、适用定稿版本/状态及首次实际运行位置；矩阵 required 与 D/A/X 未被重解释；helper 等局部修复没有无理由全量重跑；必需 manual-pending 未被当成通过。

6. **依赖最小性**：每条边能否指出实际消费接口、验证或安全顺序理由？补漏边、删无理由的边；保留 T00/迁移/验收/最终任务及组出口的必要约束。不能靠删安全边消除环；若必要依赖构成环，报告结构不成立并重划任务边界。成员实际消费前序成员接口时也要显式写依赖，members 顺序不代替接口边。逐票核对写集、共享资源与实际执行顺序。

按 [任务边界与依赖](task-boundaries.md) 走查串行成功路径：仅凭 spec、计划头部、本票与依赖接口，能否无猜测地实现和验证？共享注册文件和测试库有明确的归属、使用及释放步骤吗？逐票独立绿与汇总后的真实组合验证均须有归属；结构校验通过不能证明这些语义成立。

最后按 writing-plans「计划体量」通读整份计划：收敛重复论证和可推导细节，保留必要导航、接口、命令与断言；公共内容与任务正文一起检查，不靠搬到头部或机械拆票缩短任务。

**任务图语义审查**：存在跨模块不变量、多个切片共享写入或单票验证依赖兄弟票时，自检后、交接前交一个独立只读审查者核对任务边界、真实阻塞边和共享文件所有者。提供 spec、完整计划及必要源码指针，要求给出问题依据或无问题的覆盖说明，不传预设结论，不修改计划、不执行任务、不建 worktree。核对纵向行为是否完整、已批准替换边界是否能独立验证、汇总票职责是否与普通票 writes 矛盾，以及串行顺序是否尊重真实前置。主线程处置发现后重走受影响图；简单且无这些风险的计划沿自检即可。平台不支持或当前禁止委派时，由主线程单独做第二遍语义审查并注明未独立验证，不为此绕过限制或虚称独立通过。

按 [绑定与激活](plan-format.md#绑定与激活唯一定义点) 逐票走查实际 cwd、clear→窄提交→重新绑定的检查点及资源归属；仓库根命令使用完整仓库相对路径，进入子目录后显式返回。完成 SHA 须已存在；T00 复用隔离也有基线及状态保存，D 仅消费实际登记的所有权。

同时按 [工作区工具边界](../../using-git-worktrees/references/tool-boundaries.md) 审查实际运行能力：创建、会话 cwd 与文件工具边界分别有依据；Git 管理和宿主原生恢复方式不混用；查询结果经独立回执消费后再形成明确命令；需要原子执行的段落有已获准且兼容的稳定入口。不要把可选 RTK 包装、一次 cd 或普通终端成功当作所有宿主都能执行的证明。

路径以链接所在文档目录实际解析；尚未生成的路径在内存中解析到预期绝对位置并核对现存源文件。独立夹具仓库须写明物化步骤及后续 cwd，不能把普通嵌套目录当成 Git 根；检查 shell 引号、括号和目录切换。

保持公开行为的内部改名或 expand–contract 用前后均通过的行为保护；新行为须先让测试可执行并观察业务断言失败，导入/编译失败不算有效红。每条检查命令与当步前后的文件状态一致：迁移期间允许的旧形不能提前要求消失，contract 在删除旧定义前核对消费者已迁移，删除后再核对旧定义和依赖均已移除，并运行行为保护。文本检查须区分目标语法与同名无关内容，沿真实语法或已有解析工具，不为检查新增依赖。证据保留 stdout/stderr，以真实业务断言和退出码判断结果，不指定失败必须落在某个流。

组计划逐票走查成功和失败两条路径：定位承担修复的成员与受影响依赖闭包，保存失败原件后恢复和重新验证。按 [任务模板](task-templates.md#单文件中的纯重构与集成组) 检查待验记录、未勾选的组验证步骤及组外依赖，失败保存真实阻塞与恢复步骤。静态语法检查在内存完成，不能借自检执行生成任务或创建未登记临时文件。

获批契约内的计划缺口就地修复，并复查受影响项；发现 spec 需求没有对应任务就补任务。未决行为或契约变更回到需求澄清，沿既有批准流程处理。

绑定与交付另查：scopes 是 writes 唯一来源，以已提交范围版本作为 authority，核对 bind/inspect 的能力回执；F 依赖所有实施/组出口，A 依赖 F，D 依赖 F/A，F 不反向等待验收。逐票核对静态范围提交→适用的 authority→本地 bind 的真实提交顺序；已有记录只补当前/未执行项。验收收口必须包含简短结论、删除整个 execution 和暂存清单无 execution 文件的检查；D 给出 history_ref、实际合并事实、版本映射和资源清理，不要求转存或重读已删原件；修复后回到补验、受影响复审和验收对账，不能直接合并。
