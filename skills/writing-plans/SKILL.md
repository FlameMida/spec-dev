# 编写实施计划

## 概述

计划面向能读取仓库的执行者，写清设计取舍、文件与接口、改动要点、验证方法和必要参考；只在文字不足以明确关键约束时补代码片段。

**动笔前确认**：编写计划须持有用户的明确同意——用户本轮显式指示编写计划、或上游流程已代为确认（requirement-analysis 阶段 8 的前置确认）时视为已同意、不重复问；除此之外（如隐式触发、只收到一个 spec 路径）先确认「基于 <spec 路径> 开始编写实施计划？」再动笔。

**计划保存至**：spec 所在特性目录的 `plan/<feature-name>-plan.md`（即 `.spec-dev/YYYY-MM-DD-NN-<feature-name>/plan/<feature-name>-plan.md`，特性目录由 requirement-analysis 在写 spec 时按同日序号命名规则创建）；无 spec 输入的独立触发则自建特性目录。用户对计划位置的偏好优先于此默认值。

**单文件计划**：新计划把头部、导航、公共协议、全部任务及最终资源台账写在同一 Markdown 文件；步骤用复选框跟踪，不生成 index.md、tasks/ 或 progress.yaml。

**Spec 状态检查**：载入 spec 时读其 frontmatter 的 `spec_dev.status`——仍为 `draft` 时说明漂移守卫尚未激活（requirement-analysis 阶段 8 的激活动作未执行，常见于跨会话独立触发）：与用户确认 spec 已定稿后，把 `status` 翻为 `active` 并单独 commit，再开始编写计划；不翻转则守卫对该特性静默失效。为 `superseded` 时停下告知用户该 spec 已被取代（附 `superseded_by` 指向，指针缺失或悬空时说明"无可达后继"；沿指针链跳转时记录已访问路径，链上出现环则列出环上文件并停止），经用户显式确认才可继续按旧 spec 编写计划；正文带 `Superseded-pending` 标注时向用户提示「该 spec 正被 <新 spec> 取代中（待交付）」后再继续。无 frontmatter 的旧版/外部 spec 跳过本检查。

**上下文**：编写计划阶段不建工作区——隔离以固定的「任务 0」写入每份计划，执行时才运行（见下方"任务 0"）。

## 范围检查

本代理当前 `spec-dev collaboration: enabled` 时，拆票与交接前按 [模型协作增强](../requirement-analysis/references/model-collaboration.md) 核对必要工作、完成证据及原目标覆盖；Claude、未知模型及仅继承父代理状态者不启用。复用现有计划/spec/执行记录，不新增状态格式或批准门。

spec 聚焦单一交付物（绝大多数情况）→ 本节零动作。若 spec 覆盖多个独立子系统、或含阶段化结构（"第一阶段/Phase 1/先做 X 再做 Y"），这本应在需求设计阶段拆成子项目并登记 roadmap（requirement-analysis 的范围分解检查）；发现没拆时：

- **首选回炉**：建议回 requirement-analysis 补分解——spec 收缩到第一个子项目、其余登记 `.spec-dev/roadmaps/`，然后只为收缩后的 spec 编写本计划
- **用户不回炉**：只为第一个子系统/阶段编写本计划，剩余范围当场登记 roadmap（`.spec-dev/roadmaps/YYYY-MM-DD-NN-<project>.md`，无则新建：frontmatter `spec_dev_roadmap`（version/project/status: active）+ 子项目表（序号/名称/一句话范围/依赖/状态/特性目录），本子项目行记 `in-progress`、剩余行记 `pending`）并 git commit——**被延后的范围必须有落盘登记，不允许只活在对话里**

**一次只写一份计划，不为未实施的后续阶段预写计划**。后续阶段的接口和文件落点依赖前置交付结果，交付后再按 roadmap 续接（executing-plans 收尾会核对 roadmap 并提示下一个）。

任务分解与方案形态遵循 [design-principles.md](references/design-principles.md) 八条设计原则；同时按实际问题使用其「模块判据」。原则违反时重划；启发式须有证据，不为凑 adapter 数量新建抽象，不否决已批准 seam。计划头部保留八原则声明并引用该判据定义点。

## 文件结构先行

定义任务前，先画出将创建/修改的文件清单及各自职责——分解决策在这里锁定：

- 单元边界清晰、接口明确，每个文件一个职责
- 你对能一次装进上下文的代码推理得最好，文件聚焦时编辑也更可靠——偏向小而聚焦的文件
- 一起变化的代码放在一起：按职责拆分，不按技术分层拆分
- 既有代码库跟随既有模式；正在改的文件已经臃肿时，把拆分纳入计划是合理的，但不做无关重构

该结构决定任务分解：每个任务产出自包含、独立可理解的变更。

拆任务前读取 [任务边界与依赖](references/task-boundaries.md)：先确认共享契约与测试边界，再划可独立验证的功能切片，区分真实依赖和写入/资源冲突。将结论写入计划头部；由主线程串行执行，不因串行把任务编号误写成依赖，不生成并发声明或切换步骤。

公共接口、跨模块契约或 CLI 已有调用示例时，以其正常用法与失败结果核对任务接口及验证；旧 spec 缺示例时只从已批准契约补最小表达。发现返回语义等未决行为，回到需求澄清，不在计划里自行改变契约。

## 原型、早期闭环与验证归属

有 UI 时按[原型交接契约](../visual-preview/references/ui-prototype-contract.md#定稿与后续消费)，把 spec 中采纳的界面决定、版本及模拟边界落到对应任务的交付与验证步骤，不只在头部挂链接。关闭预览时沿已确认文字/既有界面契约。第一条真实闭环的任务归属按任务边界定义；通用澄清与界面决定直接复用已有来源。

矩阵的 required、执行时机、D/A/X 与授权条件分别传递，不重解释标记。首次 F 完整验证；后续修复按 [验证归属与按影响复验](../test-strategy/references/verification-scope.md) 写明受影响命令和有效证据复用理由，不生成小改动无条件整轮重跑的步骤。

## 任务的粒度

任务按 [任务边界与依赖](references/task-boundaries.md) 划分，每票有独立交付、验证和审查边界。步骤按实际动作写，不设固定分钟数。

按 [任务模板](references/task-templates.md) 为普通行为票内嵌有效红绿、最小实现与提交五步；获批纯重构和集成组使用其类型化步骤。完整 TDD 纪律沿 test-driven-development，不在计划中复制整套规则。

**Scenario 直译为验证**：每个 `#### Scenario:` 都有实际验证步骤；行为变化翻译为有效失败测试，纯重构使用前后保护，不能独立通过的相关验证明确归属组验证任务，不漏掉 Scenario。映射固定：GIVEN→arrange（构造前置状态）、WHEN→act（触发动作）、THEN→assert（断言可观察结果）；测试名沿用 Scenario 名。规范到测试零翻译损耗——不要自己另编测试场景后把 Scenario 丢在一边。测试步骤的 Lane 归属与 DB/前端/Agent 处方遵循 test-strategy skill（矩阵行标注的 lane 直接继承；DB 类步骤对照其 references/db-testing.md，不得出现每测试一容器）。

## plan 目录结构

```text
.spec-dev/<特性目录>/plan/<feature>-plan.md
```

文档内依次为头部与公共协议、四列任务导航、`### 任务 0` 至最终任务；每步使用 `- [ ] **步骤 N：…**`。任务多时按真实行为/工作域分组，编号全局连续；分组只辅助阅读。资源台账内嵌最终任务。

## 按动作读取

| 动作 | 必读资料 |
|---|---|
| 写头部、任务导航、scopes、绑定与复选框进度 | [计划格式](references/plan-format.md)；编写任何新计划前读取 |
| 写 T00、普通行为票或纯重构票 | [任务模板](references/task-templates.md)；写清改动、接口、命令与预期结果 |
| 从 spec 划任务、判断哪些票能独立推进 | [任务边界与依赖](references/task-boundaries.md)；核对共享契约、纵向切片、依赖理由和共享写入 |
| 写独立 final F、验收 A 和最大号交付 D | [验收与交付模板](references/delivery-templates.md)；保留 F→审查→A/对账→D 顺序 |
| 草稿 Self-Review 与恢复修订 | [计划自检](references/plan-review.md)；核对实际状态提交与资源归属 |

执行命令、必要实参和失败分支必须进入计划；共用协议可通过计划头部的明确节名指针复用。已知持久资源在最终任务的资源台账预登记。

## 计划体量

- **改动要点 + 验证依据**：给出文件/符号落点、目标行为、接口约束，以及测试的前置输入、动作、预期结果和运行命令。执行者据此写测试与实现；不要求计划预写完整测试、函数体或新增文件全文。
- **片段按需**：关键签名、易歧义算法或精确文本替换需要时给最小片段；既有代码用路径/符号定位，避免整文件复制。
- **整份计划的信息密度**：自检时收敛重复论证、可从代码直接推导的细节和无助执行的片段，保留关键决定、接口、具体断言与命令，以及导航和任务接口块的必要重复。任务按真实交付、验证和审查边界划分，不以行数、篇幅比例或拆票数量为目标。

## 禁止占位符

不能把未决设计留给执行者：如 TBD、未指明错误/边界的“添加校验”、没有输入和预期结果的“写测试”、只说“类似任务 N”或引用未定义且无来源的接口。具体行为、断言和运行命令齐全时，缺少代码片段不构成占位符。

## 执行交接

保存计划后按 [计划自检](references/plan-review.md) 完成适用的任务图语义审查，再展示最新计划文件链接与简短变更摘要，列 2–3 个针对粒度、依赖或边界的陈述式检查点；交代实际依赖和共享资源边界，再作一次整体确认。检查点不附“请确认”“是否接受”等问题；确有未决点则先按一次一题澄清。保存、校验和提交状态以实际工具回执为准，稿件审阅认可不等于开始实施授权。向用户交接：

> 「计划已完成并保存至 `.spec-dev/<特性目录>/plan/<feature>-plan.md`。执行时我会用 executing-plans 从任务 0（隔离工作区）开始，由主线程逐任务串行执行，保留 TDD、每任务提交与收尾审查。
>
> 现在开始执行，还是先 review 计划？」

本计划属于某 active roadmap 的子项目时，话术首句追加进度锚点「（roadmap `<project>` 第 N/M 个子项目）」——让用户在交接时刻看到全局位置。

交接说明执行顺序、真实前置与资源限制，仅确认「开始执行 / 先 review」；已有执行授权不重复询问。执行只有主线程串行路径。开始后统一交给 executing-plans——未回复、或只给了计划修改意见时不得启动执行；用户要改计划则修订后重跑 Self-Review。
