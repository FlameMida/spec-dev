# 编写实施计划

计划面向能读取仓库的执行者：写清做什么、改哪里、接口是什么、怎么验证。计划文件是执行期唯一的事实源，执行者只凭它和 git 记录就能开工、中断后也能接着做。

## 开始之前

**持有同意才动笔**。用户本轮明确要求写计划，或 requirement-analysis 的设计已获批准（批准设计即同意写计划），都不重复问。只收到一个 spec 路径这类隐式情形，先问一句「基于 <spec 路径> 开始编写实施计划？」。

**保存位置**：`.spec-dev/YYYY-MM-DD-NN-<feature>/plan/<feature>-plan.md`，与 spec 同一个特性目录。没有 spec 时自建特性目录：NN 是当日两位序号，扫描 `.spec-dev/` 下当日已有的日期前缀产物取最大加一。用户指定位置优先。

**输入**：

- 有 spec：读全文。状态是 `superseded` 时停下告知，并沿 `superseded_by` 找后继；`draft` 是实施期间的正常状态，直接使用。
- 没有 spec，需求本身已是可验证清单：在计划头部写「验收标准」，每条一个可观察结果，作用等同 Scenario。
- spec 的关键决策里有界面定稿：读定稿 HTML、界面约定摘要、组件映射表和还原要点。它们由 visual-preview skill 产出，原型的版本与确认规则以该 skill 为准。
- 需求还有设计空间（多种做法、行为没说清）：建议先走 requirement-analysis，不在计划里替用户做设计决定。

## 范围检查

一份计划只承载一个可交付目标。spec 覆盖多个独立子系统，或写了"第一阶段、第二阶段"时：

- 首选回 requirement-analysis 拆成 roadmap 子项目，spec 收缩到第一个。
- 用户不回炉：只为第一个子项目写计划，其余范围登记进 `.spec-dev/roadmaps/` 并提交。被延后的范围必须落盘，不能只留在对话里。

不为还没实施的后续阶段预写计划，它们的接口和落点取决于前一阶段的交付结果。

## 先定文件结构，再切任务

列出将创建和修改的文件及各自职责，分解在这里定型：

- 每个文件一个职责，接口明确；一起变化的代码放在一起，按职责拆而不是按技术层拆。
- 偏向小而聚焦的文件，执行者对能一次读完的代码推理得最好。
- 既有代码库跟随既有模式；正在改的文件已经臃肿时可以把拆分纳入计划，不做无关重构。

然后按 [任务边界与依赖](references/task-boundaries.md) 切任务：每个任务交付一个可演示或可验证的行为，只在真实需要时建立依赖。方案取舍与分解遵循 [设计原则](references/design-principles.md)。

## 任务怎么写

按 [计划模板](references/plan-template.md) 落笔。要点：

- **Scenario 直译为测试**。每个 Scenario 至少落到一个任务的失败测试：GIVEN 是准备、WHEN 是动作、THEN 是断言，测试名沿用 Scenario 名，在公共边界（API、CLI、页面、模块公共函数）观察行为。不要另编一套测试场景把 Scenario 晾在一边。
- **第一个任务打通最薄的一条端到端路径**。让第一条真实用户流程尽早跑通，后续任务在它上面加能力。
- **界面任务带上定稿**。spec 采纳了界面定稿时，头部写定稿的路径与版本；每个界面任务写明对应的定稿屏与状态、组件映射行和还原要点，测试断言取自定稿里可观察的结构、文案和状态。界面任务在确认绿之后加一步还原自查，写明怎么启动应用、打开哪个入口，以及角色、数据、视口和状态。用户在批准计划时说不做还原自查的，不写这一步。
- **接口写精确签名**。每个任务写明消费哪些前序产物、产出什么函数名、参数和返回类型；执行者只读头部、本任务和依赖任务的接口行就能开工。
- **测试命令写全**。头部给出四种命令：单个测试、快检（项目已有的 typecheck 或 lint，没有写"无"）、受影响范围、全量。任务步骤只使用前两种。
- **给改动要点，不预写全文**。写文件和符号落点、目标行为、测试的输入动作断言和运行命令；关键签名或易歧义的算法才给最小片段。
- **纯重构**用前后都通过的行为测试保护，不伪造失败。
- **禁止占位符**。TBD、没有输入和预期的"写测试"、没说明错误与边界的"加校验"、"类似任务 N"，都是把未决设计留给执行者。行为、断言和命令齐全时，没有代码片段不算占位符。

发现接口返回语义等行为没定，回到需求澄清，不在计划里自行决定契约。

## 收尾不写进任务

隔离工作区、回归测试、验收、合并都不作为计划任务，由 executing-plans 承担：工作区在开工时建立，回归和验收在全部任务完成后先问用户再做。

计划头部的「收尾预先决定」默认写"做完再问"。用户在批准计划时已经说明怎么做（例如"回归跑受影响范围，不做验收，走 PR"），就原样记下。

## 自检

交接前对照 spec 过一遍：

1. **覆盖**：每条 Requirement 能指到实现它的任务吗？每个 Scenario 都有对应的测试步骤吗？修改既有功能时，MODIFIED 和 REMOVED 有对应的改造与清理任务吗？有界面定稿时，每个定稿屏与状态、组件映射里每个新增或扩展的组件都落到任务了吗？
2. **可执行**：文件、符号、接口、输入、动作、断言、运行命令都明确吗？有没有占位符？
3. **接口一致**：后续任务用到的类型、签名、属性名与前序任务的产出一致吗？导航表与任务正文逐条对得上吗？
4. **依赖最小**：每条依赖都能说出消费了哪个接口或哪条安全顺序吗？有没有环？
5. **闭环与命令**：第一个任务形成真实闭环了吗？四种测试命令都写了吗？

计划缺口就地补；spec 里的需求没有对应任务就补任务；发现未决行为回需求澄清。

## 执行交接

保存后给出计划路径、任务数与依赖概况，列 2 到 3 个针对粒度、依赖或边界的陈述式检查点，然后问：

> 「计划已保存至 `<路径>`。批准后我用 executing-plans 执行：建隔离工作区，逐任务 TDD 并提交，全部完成后先问你，再做回归、验收和交付。现在开始执行，还是先改计划？收尾怎么验可以现在定，也可以做完再问。」

计划含界面定稿时，在交接里说明界面任务带还原自查：每个界面任务转绿后会启动应用、打开浏览器对照定稿，用户可以要求去掉。

批准计划等于授权执行，交给 executing-plans。用户没回复或只给了修改意见时不启动执行；改完计划重新自检。本计划属于某 roadmap 的子项目时，话术开头注明是第几个子项目。
