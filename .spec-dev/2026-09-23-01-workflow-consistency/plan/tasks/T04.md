## 步骤 3：实现逐视图核心

- 抽出已有 frontmatter/glob 纯算法到 spec-data，不改原合法格式处理；loadActiveSpecs 接收 view，不再所有模式都读可变 checkout。
- `--staged` 用 `git ls-files --stage -z` / `git show :path`；commit 用对应树/父树；删除与 rename 两端使用 `--no-renames -z` 取得实际受影响路径。链接检查分别在旧/新树，不能只查最终 realpath。
- 工作区/显式文件入口可读有效本地 receipt；range/push 不用它，逐提交解析 Spec-Task、在该提交上下文核验范围。merge 提交按各父差异核对，不悄悄忽略冲突解决。
- 每个 ref 独立累积自己的 violations；一个提交触及 spec 不能替代另一个提交的关联。普通未绑定路径保留原同步与明确例外含义。
- 新任务关联与宽跳过同时声明视作冲突，不能让无效 binding 落入旧 fail-open 或 off 快捷出口；需要使用已授权宽例外时，先明确退出本任务关联再沿原规则操作。加入这组正反例，无关联的原例外含义不变。

git-view.mjs 导出 `class ScopeViolation extends Error { constructor(message){ super(message); this.name='ScopeViolation'; } }`；主入口导入同一类，将新绑定读取/对象缺失/版本失败转为此错误。存在绑定时先校验，再走“没有 active spec”早退，不能通过删除/降格声明令无效绑定静默消失。

核心分流替换：
```js
const hit=changed.filter(file=>file!==spec.relPath&&spec.matches(file));
if(hit.length&&!specTouched){
 const allowed=binding!==null && binding.specs.includes(spec.relPath)
   && hit.every(file=>binding.writes.has(file));
 if(!allowed)violations.push({spec:spec.relPath,feature:spec.feature,code:hit});
}
```
该段之前必须完成 binding 的版本、当前视图和路径校验；不能在此以 field 存在代替验证。历史分支返回 `{commit,ref,violations}`，不是路径并集。

错误出口：
```js
if(error instanceof ScopeViolation){
 console.error(error.message);
 process.exit(MODE==='--hook'||MODE==='--worktree'?2:1);
}
```
原异常警告兼容仅适用于非绑定旧流程；声明了任务关联而无法读取必要 Git 对象也属于 ScopeViolation。`stop_hook_active` 不豁免无效新绑定。
