## 步骤 3：按权威改写

| 旧规则 | 新规则与实际步骤 |
|---|---|
| current/已完成任务的 commit 都必须可解析，只取 pending | completed 必须有完成提交；先恢复 current 的 in_progress/blocked；无当前票再 ready；组/parallel 分支单独引用 |
| 全量首次运行在最终任务 | 独立 F：依赖实施出口→运行并记录全量→失败归属→保存 F；A 消费 F；D 只消费有效回执和审查/对账 |
| 最终全量失败修复后直接合并 | 修复记录新候选，补验影响闭包、复审对应维度、更新验收/对账后再交付 |
| execution 原件提交到 Git | 实际 record，提交引用；T08 transfer 原件并核验后才清理 |
| 所有任务/组 SHA 必须祖先于目标 HEAD | 活动和票级仍严格；最终 squash 按 delivery/source 历史与目标关系核验 |
| pass 一律独立审计 | light/standard 证据与 coverage_note；deep 审计全部 pass 并抽查至多两项；fail/warn 保留复核 |
| 零候选一律不派 critic | 使用 T11 的完整条件表；large 冲突配置明确拒绝 |

T00 模板保留原来源/资源/基线绑定；生成模板不要求在 task-scope 实现存在之前调用它。新计划写 scopes 共用块，parallel 只列 resources；旧计划恢复局部迁移不改 completed。绑定激活在静态声明与状态 checkpoint 提交后，关联到实际历史 commit；prepare/commit-msg 使用真实安装路径。

含 scopes 的计划必须收到 plan-index 的 `scope_protocol_version:1`；旧工具仅回 ok 不能证明支持，缺能力时停止相关新协议动作并说明实际缺口。引导计划无新块时不伪造该回执。

交付模板必须内嵌 transfer CLI、目标/来源/历史 ref 核验、台账结果保存、sync_commit 和最终 checkpoint 的实际命令；不以“按协议处理”替代步骤。legacy 单文件用原台账/复选框及新静态块，不生成第二个 progress。

核验字段从“写进说明”连接到实际 T09 校验器，T07/T10 的 record/verify 明确工具 exit0 与被测 exit_code 的区别。技能文档描述 Snapshot 仍严格，不能写成“进度变化允许同 run 续跑”。
