# 探索：测试/过期代码累积处理 + spec handoff 文件（2026-08-09）

## 问题

1. 项目推进中测试与过期代码累积，每次开发完成需跑大量测试，需要处理机制（用户设想：计划设计时纳入考虑；按模块分组关键测试、只跑涉及模块的测试）。
2. spec 产出时额外产出会话上下文/handoff 文件，方便切换 AI 后继续编写 plan。

## 关键发现（含代码证据）

- 套件现有两处全量测试：worktree 基线全绿验证（`skills/writing-plans/SKILL.md:113`）与计划最终任务的全量验证（`skills/writing-plans/SKILL.md:190`、`skills/executing-plans/SKILL.md:90`）；任务间只跑各自 TDD 测试。痛点真实且随项目规模线性恶化。
- spec frontmatter 的 `covers` glob 是现成的"模块 → 测试范围"映射锚点，可推导受影响测试集。
- 过期代码清理已有部分承载：spec 差量三节 REMOVED → writing-plans 清理任务；roadmap 子项目③ resource-ledger 管测试**资源**（环境/缓存/产物）台账清理——与"过期测试退役"是相邻但不同的轴。缺口：没人负责测试的退役，测试只增不减。
- 套件哲学：spec 是唯一交接物，writing-plans 假设读者零上下文。换 AI 真正会丢的只有探索期的代码证据（集成点、file:line 线索）。

## 结论（用户已认可）

1. **想法 1 做**：登记为 roadmap skill-flow-upgrade 子项目④（测试分域执行 + 测试退役纪律），与③零耦合可并行。中间验证跑 `covers` 推导的相关测试范围，最终任务合并前保留全量安全网（glob 选测会漏跨模块回归）。
2. **想法 2 降级做**：不做独立 handoff 文件（易过期、质量难约束），改为 spec 模板加可选"实施线索附录"节（关键文件路径、集成点、已验证代码事实）。

## 未决问题

- 测试分组粒度：按 `covers` glob 自动推导 vs 计划里人工声明——留给正式设计裁决。
- 想法 2 规模接近 quick-fix，是否并入子项目④一并设计或单独走。
