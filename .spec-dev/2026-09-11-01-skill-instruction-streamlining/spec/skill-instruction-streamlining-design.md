# 技能指令精简、按需分层与文档规范统一设计

## 背景与目标

在不减损既有交付、测试、审批和资源安全约束的前提下，完成本轮审查剩余的 19 项整改：压缩触发描述，按任务条件装载详细规则，消除固定执行路径与机械请示，统一 DDD 文档规范并修正两处说明冲突。

本设计依据当前会话的逐项审查、用户裁决和项目现行产品文件；代码基准为 `179d76a7`，插件版本为 8.5.0。本次未读取既有 `.spec-dev/` 档案内容，不能用历史批准、旧验收或旧计划支撑结论。旧档案的工作区删除状态不归本次所有，不恢复、提交或清理。

成功标准：19 项逐一有实现归属与验证场景；规则仍有唯一权威及有效引用；应保留的 30 项约束语义不变；排除技能及其更新逻辑内容不变；静态检查与模型行为证据分别报告，不以文档变短证明模型效果。

## 用户决定与授权边界

以下决定均来自本会话，不引用旧档案：

1. 用户要求“除了应保留的全都进入需求分析”，最初纳入 A01—A20、C01—C03；B01—B30 为保留约束。
2. 用户随后要求“两个跟随上游更新的 skill 不纳入更改”：排除 AnySearch、sequential-thinking 及专属配套文件、上游更新逻辑；A01、A08、A12、A20 撤出，剩 19 项。取消 sequential-thinking 强制调用的上游调整也随 A12 撤出。
3. C03 最终选择“全部统一”：DDD 无论独立使用还是被主流程调用，均采用 spec-dev 的文档位置与保存规则；不存在独立模式继续使用 CONTEXT/docs 的分支。
4. 整体采用方案一：保留现有技能入口和规则归属，在各自配套资料中分层，不新增插件级公共规则框架。
5. 用户于完整设计展示后回复 `ok`，批准本设计落盘及审查；不是实施授权。spec 审阅和后续编写计划仍按当前工作流交接。

“保留”指约束语义保留，允许为已批准的分层移动正文并更新引用；不能借移动取消约束。两个排除技能则以文件内容不变为边界。

## MODIFIED Requirements

### Requirement: A02 执行计划描述只承担触发和职责说明

executing-plans SHALL 在 description/openai 摘要中保留已批准书面计划的入口、执行职责和即兴修改的排除边界，将状态字段、任务目录细节和并发准入全文留在正文或导航。

#### Scenario: S01 已批准计划仍触发执行技能
- **GIVEN** 用户明确要求执行已批准书面计划。
- **WHEN** 从压缩后的描述选择技能。
- **THEN** 仍选择 executing-plans，并能经入口取得实际计划格式与恢复规则。

#### Scenario: S02 即兴小修不因执行关键词误触发
- **GIVEN** 用户只要求修复一个单点问题，没有书面计划。
- **WHEN** 进行技能选择。
- **THEN** 不误用 executing-plans，不为满足描述而创建计划。

### Requirement: A03 验收描述保留验收与日常测试分界

acceptance-qa SHALL 保留功能/页面/接口验收、适用诊断与日常测试/代码审查/文档审查的排除边界，移出工具枚举和重复触发例句。

#### Scenario: S03 验收请求仍覆盖原适用维度
- **GIVEN** 用户明确要求对功能做验收或对页面交互故障做适用诊断。
- **WHEN** 读取精简描述。
- **THEN** 选择对应验收路径，并按目标与矩阵选维度，不因删工具名丢失性能、视觉或诊断入口。

#### Scenario: S04 日常跑测试不进入验收编排
- **GIVEN** 用户只要求运行现有单元测试。
- **WHEN** 选择技能。
- **THEN** 不触发 acceptance-qa 的全套编排。

### Requirement: A04 探索描述聚焦未承诺交付状态

exploring SHALL 在精简描述中保持未承诺交付、受控 spike 和正式设计交接边界，以少量例句代替近义表达清单。

#### Scenario: S05 未定想法进入探索
- **GIVEN** 用户尚未决定是否实施某个想法。
- **WHEN** 选择入口。
- **THEN** 进入探索，默认只读，不自动建立实施档案。

#### Scenario: S06 已承诺交付不被留在探索
- **GIVEN** 用户明确要求落地功能，或只有单点事实问题。
- **WHEN** 选择入口。
- **THEN** 分别进入适用开发流程或直接回答，不误用探索；受控 spike 不被解读为任意写码许可。

### Requirement: A05 需求描述保留设计空间与相邻入口边界

requirement-analysis SHALL 以已承诺、有设计空间的开发需求及获批 spec 为描述核心，不在描述中重复展开八阶段操作。

#### Scenario: S07 新行为设计正常触发
- **GIVEN** 用户要求设计并落地一个有真实取舍的新行为。
- **WHEN** 读取描述。
- **THEN** 进入需求设计，后续仍经过当前正式设计门。

#### Scenario: S08 小修和已有批准 spec 不重复设计
- **GIVEN** 请求分别为无设计空间小修、或基于批准 spec 编写计划。
- **WHEN** 选择入口。
- **THEN** 分别进入 quick-fix 或 writing-plans，不因描述泛化重新走完整需求设计。

### Requirement: A06 计划技能按任务形态加载详细规范

writing-plans SHALL 通过导航分层提供格式、资源、声明、模板与自检规范，同时使生成计划保持适用内容完整和独立执行能力。

#### Scenario: S09 普通计划不加载组和并发专项
- **GIVEN** 新计划不含集成组或并发声明。
- **WHEN** 作者取得计划格式及普通任务模板。
- **THEN** 能生成完整三件套，不要求读取组或并发专项；普通字段与资源台账可经唯一来源定位。

#### Scenario: S10 特殊计划和脱离插件交付仍自足
- **GIVEN** 计划获准采用集成组，且需让零上下文执行者使用。
- **WHEN** 生成相关任务。
- **THEN** 在生成前取得完整适用协议，产物包含命令、代码、接口、验证及恢复步骤，不用插件链接代替实际操作。

### Requirement: A07 需求主文件保留阶段门并按需装载生命周期

requirement-analysis SHALL 保留八阶段导航和用户裁决门，将文档生成、生命周期及详细审查规则移至对应专题，并在相关阶段前加载。

#### Scenario: S11 分诊不预载后续写入细则
- **GIVEN** 本轮仍处于需求理解与只读探索。
- **WHEN** 加载主入口。
- **THEN** 可识别流程和批准边界，不无条件加载完整 ADR、编号、取代写入与审查模板。

#### Scenario: S12 写入和审查不因拆分失去规则
- **GIVEN** 完整设计已获批准，将进入 spec 生成或审查。
- **WHEN** 处理对应阶段。
- **THEN** 先读取适用全文；定义缺失如实报告，不跳过保留的写入、生命周期或审查义务。

### Requirement: A09 小修反查和守卫规则按条件提供

quick-fix SHALL 保留反查必做、契约分流和升级条件，将发现/status 链及具体守卫操作拆为动作前读取的专题。

#### Scenario: S13 没有安装守卫仍执行契约反查
- **GIVEN** 嫌疑文件范围已确定，但目标仓库未装编辑守卫。
- **WHEN** 进行小修。
- **THEN** 仍按完整五条 glob、covers 和状态语义反查；不无条件加载编辑闸放行全文。

#### Scenario: S14 命中守卫先取得对应机制
- **GIVEN** 文件命中 active spec 且相关写入或提交受守卫影响。
- **WHEN** 准备执行该动作。
- **THEN** 先取得适用守卫规则；不得以按需分层为由静默绕过或伪造 spec 同步。

### Requirement: A10 共享入口按动作选择完整权威

RA/exploring SHALL 先取得短共享入口，再根据材料归属和下一动作取得来源、派发、插件根或输出契约的适用定义，复用已经取得的当前定义。

#### Scenario: S15 内部轻量调查只取得适用规则
- **GIVEN** 当前任务仅检查内部代码，无外部研究或代理派发。
- **WHEN** 加载入口并调查。
- **THEN** 不强制读全部外部派发和恢复细则；澄清核心和材料分类等适用边界仍生效。

#### Scenario: S16 条件变化先补规则再行动
- **GIVEN** 后续出现第三方能力核查或需要派发子题。
- **WHEN** 转入该操作。
- **THEN** 动作前取得完整对应权威；不以主线程曾读代替新 worker 取得，也不循环重读同一当前定义。

### Requirement: A11 并发详细协议按状态边界加载

并发技能 SHALL 在主入口保留准入、职责和核心不变量，以专题提供锁、激活/切换恢复及接收集成，保持协议语义不变。

#### Scenario: S17 初次并发与串行组可定位适用协议
- **GIVEN** 一个已批准并发执行入口和一个仅需共享特性锁的串行 v2 入口。
- **WHEN** 准备受保护状态写入。
- **THEN** 都能取得同一锁权威；后者不必加载无关的全部并发模式说明；取锁前不得写状态。

#### Scenario: S18 中断恢复不按普通首次启动猜测
- **GIVEN** 已有中断的 claim、模式切换或未接受结果。
- **WHEN** 恢复或接收。
- **THEN** 先取得对应完整专题并核验实际状态；未知 owner、差异或证据仍按原协议阻塞。

### Requirement: A13 独立子题按实际容量尽早派发

探索编排 SHALL 允许同波次多调用和容量分批，不以单消息作为正确性门槛，也不无故串行等待独立主题。

#### Scenario: S19 容量不足分批完成同一覆盖
- **GIVEN** 五个独立主题和两个可用 worker 槽位。
- **WHEN** 编排探索。
- **THEN** 分批启动、回收并覆盖全部主题，不为一次性派发发出超容量调用或宣称未启动项完成。

#### Scenario: S20 容量足够不逐个立即等待
- **GIVEN** 两个相互独立、输入齐全的子题及足够容量。
- **WHEN** 派发。
- **THEN** 尽早启动二者，只在需要结果时等待；依赖未定的子题不被假装独立。

### Requirement: A14 步骤和粒度依据任务类型

writing-plans SHALL 取消跨所有任务类型的“超过五步必拆”，继续采用普通行为票五步以及其他类型各自完整步骤。

#### Scenario: S21 合法收尾任务不会因七步被拆散
- **GIVEN** 一个有完整交付生命周期的七步最终任务。
- **WHEN** 检查粒度。
- **THEN** 不仅因步数判定任务过大或拆散必要顺序。

#### Scenario: S22 普通行为票不借此取消五步
- **GIVEN** 普通行为实施任务。
- **WHEN** 生成任务。
- **THEN** 有效红、最小实现、绿与提交的五步保持；多个独立交付物不因取消计数门而塞入一票。

### Requirement: A15 项目就绪动作由实际配置决定

worktree 就绪及计划 T00 SHALL 根据项目声明、锁文件和已有环境选择必要安装/构建命令，不用单个清单文件直接推断唯一包管理器。

#### Scenario: S23 已就绪的 pnpm 项目不被强制 npm 安装
- **GIVEN** 项目明确采用 pnpm，环境已有可用依赖。
- **WHEN** 建立或复用隔离环境。
- **THEN** 核实就绪并运行适用基线，不强制 npm install 或创建另一种锁文件。

#### Scenario: S24 缺依赖按项目工具补齐
- **GIVEN** 项目有 pyproject.toml，但声明使用非 Poetry 工具且依赖未就绪。
- **WHEN** 准备基线。
- **THEN** 使用项目已声明命令；声明冲突先核实，无法确定时报告缺口；不跳过基线或凭文件名安装 Poetry。

### Requirement: A16 探索报告按有界问题组织

code-explorer SHALL 必填直接结论、关键证据及覆盖缺口，其余 Markdown 栏目按相关性提供；显式 JSON 模式继续满足原 schema。

#### Scenario: S25 单接口核查不凑八节
- **GIVEN** 子题只要求核对一个公共接口的签名。
- **WHEN** 输出报告。
- **THEN** 给直接结论、实际位置和范围；不编造无关架构、技术债或性能分析以填满八节。

#### Scenario: S26 契约报告仍保留必填覆盖信息
- **GIVEN** 派发明确要求 exploration-report JSON。
- **WHEN** 回报。
- **THEN** 原 keyFiles、coverage_note 等机器约束保持；宽题中真实相关依赖和风险仍应报告，不借简短输出静默缩范围。

### Requirement: A17 精简劝诫而保持测试纪律

TDD 文档 SHALL 删除或移出重复训诫和借口对照，将完整规则及必要完成条件保留在单点，不改变其执行语义。

#### Scenario: S27 精简后仍先取得有效行为红
- **GIVEN** 需要新增行为且无适用例外授权。
- **WHEN** 使用精简后的纪律。
- **THEN** 仍先观察有效失败，再最小实现和验证通过；已先实现的违规处置不因此消失。

#### Scenario: S28 纯重构和例外仍按原规则处理
- **GIVEN** 一例获准纯重构和另一例已获同范围例外授权。
- **WHEN** 执行。
- **THEN** 前者保留前后行为绿，不伪造红；后者复用既有决定，不重复询问，也不将例外扩大到新范围。

### Requirement: A18 验收遵循矩阵和计划指定时机

acceptance-qa SHALL 按目标、矩阵和计划执行到期检查，不在子阶段无条件追加全量套件。

#### Scenario: S29 局部验收不自行追加全量
- **GIVEN** 变更只涉及一个模块，矩阵和计划未要求此时全量回归。
- **WHEN** 验收该变更。
- **THEN** 执行相关检查并记录范围；尚未到期的最终全量保持待执行。

#### Scenario: S30 已规定的全量和独立复跑不能被省略
- **GIVEN** 当前到达获批最终全量或必要独立复跑的时机。
- **WHEN** 执行该检查。
- **THEN** 不用早前局部绿或“减少重复”抵消它；变更后的补验及新增/既有失败分类保持。

### Requirement: A19 证据驱动的契约影响分流

quick-fix SHALL 将契约影响作为现行要求、实现行为和拟议修复的证据判断；步骤 4 消费该判断及适用用户决定，不再固定依赖一次人工答案。

#### Scenario: S31 恢复既定行为直接消费证据判定
- **GIVEN** 现行 Requirement/Scenario 明确，实际实现偏离，修复仅恢复原行为且范围已授权。
- **WHEN** 判定契约影响。
- **THEN** 给出引用及理由并继续契约不变分支，不固定询问“这是不是契约变化”；有效红及守卫边界保持。

#### Scenario: S32 新语义和冲突仍需对应裁决
- **GIVEN** 修复会改变现行可观察行为，或两份现行要求矛盾/证据不足。
- **WHEN** 分流。
- **THEN** 前者进入 spec 同步和原有批准；后者列出真实分歧及证据缺口，保留原升级门。事实判断不自动授权新语义、绕过编辑闸或选择冲突的一方。

#### Scenario: S33 无命中 spec 不制造人工契约题
- **GIVEN** 按原范围完成反查但未命中适用 spec。
- **WHEN** 处理明确的小修。
- **THEN** 如实记录未命中，以已知需求及适用测试边界处理，不编造契约，也不询问缺少对应依据的问题。

### Requirement: C01 浏览器 MCP 能力按实际配置说明

验收文档 SHALL 统一说明插件不分发浏览器 MCP，使用目标项目实际可用能力及适用降级路径，不声称安装插件即完成浏览器配置。

#### Scenario: S34 未配置浏览器 MCP 如实降级
- **GIVEN** 仅安装本插件，项目未自配浏览器 MCP。
- **WHEN** 装配验收能力。
- **THEN** 不报告自动生效；使用适用现有工具或标记未验证，不自动写全局配置。

#### Scenario: S35 已有能力正常复用
- **GIVEN** 项目已有可核验的浏览器能力。
- **WHEN** 验收需要它。
- **THEN** 正常复用；配置无效报告实际故障，不将本地受控审查 stdio 工具等同浏览器 MCP。

### Requirement: C02 计划模板要求具体行为断言失败

计划模板 SHALL 用 Scenario 的可观察结果表达预期红，将未定义符号、编译或环境故障标为测试尚不能证明行为的阻碍。

#### Scenario: S36 预期失败指出业务差异
- **GIVEN** 存在可运行公共边界或获准的受控基线，其行为未满足目标 Scenario。
- **WHEN** 写失败测试步骤及预期。
- **THEN** 给出具体行为断言的期望与实际差异，而不是把 function not defined 当成功取得行为红。

#### Scenario: S37 测试未运行到行为断言不算有效红
- **GIVEN** 测试只产生 NameError、import failure、编译错误、零测试或 SKIP。
- **WHEN** 判断红证据。
- **THEN** 标明实际阻碍并按原路径处理，不虚构业务失败，不先实现目标行为来制造红。

### Requirement: C03 DDD 统一文档位置、保存与生命周期

DDD SHALL 在独立和被引用两种用法中统一消费 spec-dev 文档规范：共享术语进入 `.spec-dev/glossary.md`，局部术语留对应 spec，ADR 进入 `.spec-dev/adr/`；保存须有设计或保存范围授权，且同范围直接复用。

#### Scenario: S38 独立与被调用使用相同新文档约定
- **GIVEN** 两次相同的建模请求分别独立调用 DDD 和经 RA 调用，且保存范围已批准。
- **WHEN** 需要记录共享术语和合格 ADR。
- **THEN** 两者均采用同一位置和生命周期，不再分别生成 CONTEXT/docs 与 glossary/adr 两套新规范。

#### Scenario: S39 未获保存授权保持候选并复用后续授权
- **GIVEN** 术语已讨论清楚但没有保存授权，随后用户批准该保存范围。
- **WHEN** 先后处理候选术语及同范围增量。
- **THEN** 批准前只保留对话候选，批准后可保存并继续同范围增量，不逐个术语重新询问；新行为或新范围仍按原门处理。

#### Scenario: S40 多域、局部术语及无内容不产生重复记录
- **GIVEN** 两个领域使用同名不同义概念，另有仅适用于当前特性的术语，且没有合格 ADR。
- **WHEN** 组织文档。
- **THEN** 共享概念通过适用域区分，局部概念留相应 spec，不生成空 ADR；没有适用 spec 时不擅自启动新特性，候选沿已有授权暂存或交接。

#### Scenario: S41 旧位置和冲突不触发自动迁移
- **GIVEN** 用户项目已有 CONTEXT.md、docs/adr/ 或另一份词汇表，内容可能与当前候选冲突。
- **WHEN** 在获授权的目标任务中遇到这些资料。
- **THEN** 不自动搬移、删除或双写；真实冲突展示来源和差异后沿现行规则处理；本次整改自身不扫描历史文件来制定迁移清单。

## 统一文档规范细节

共用定义放在 requirement-analysis 的配套文档内，建议名 `references/document-conventions.md`。RA、context-reuse 与 DDD 只保留导航及各自职责，不复制三套保存规则。

- 跨特性领域术语记录规范名、简短定义、Avoid、适用域和决定来源；通用编程术语与实现细节不收录。
- 局部术语只进入对应 spec；没有适用 spec 时不自动编造完整特性档案，沿既有候选/保存/交接出口处理。

- 用户明确位置要求优先；没有覆盖性指令时，两种 DDD 用法采用同一默认位置。尊重具体用户指令不是恢复两种默认模式。
- 完整设计批准或明确保存范围均可提供相应写入授权；只授权术语保存不等于批准新的行为义务。已有同范围授权直接复用。

- 原许可及来源保留，`references/ATTRIBUTION.md` 的“原文逐字收录/唯一修改”说明随实际适配如实更新；不修改两个排除技能的上游更新机制。

## 测试与验收策略

### 公共测试落点声明

1. 描述/规则的行为落点是客户端从真实技能入口执行的有界任务：观察技能选择、实际读取路径、派发/等待、询问、命令选择和产物，不以模型自述判 PASS。
2. 结构落点是现有文件及导航、`scripts/validate-output.mjs` 的既有 schema/plan-index 契约、`scripts/check-openai-sync.mjs` 的元数据结构与同步约束，以及现有相关 node:test 测试。
3. 允许替换夹具中的外部服务、平台容量和环境可用性，以覆盖分批、缺件及批准状态；真实用户授权由夹具明确给定。不能替换被测技能决策本身，不能用 fake model 通过证明真实模型行为。
4. 文件系统/命令/模型等真实 IO 按 PR 或 nightly 归类；纯内存数据及断言属于 fast。不新增 HTTP、DB 或私有测试接口。

## 风险与防守

1. 拆分后出现循环读取、失效锚点或摘要替代权威：以实际入口和专题条件走查；保留旧公共入口作为导航，禁止重复完整定义。
2. 精简描述误扩大或缩小触发：保留正例/近似负例并做实际模型检查；只看字符数不作成功判据。
3. 移动锁或台账规则时改变协议：来源段落与现行消费者逐项核对；字段、状态和恢复语义不得变更。
4. DDD 子文件继续提供旧规范：主文件、modeling、模板与规范性说明同次核对，来源修改声明准确；历史迁移不自动进行。
5. 测试恰好因旧位置断言而失败：先区分位置变化与语义丢失，再修改断言；保留有效失败和后续通过证据。
6. 本次提交卷入已有删除或自动发版：限定本次新增文件，核对暂存区；纯设计提交使用仓库提供的跳过开关避免安装式包检查和发版副作用，单列实际文档检查，不宣称执行了被跳过的检查。
